# Model Context Protocol（MCP）

LangChain4j 支持 Model Context Protocol（MCP），用于与符合 MCP 规范、可提供并执行工具的服务器通信。有关该协议的通用信息，请参阅 MCP 官网 (opens new window)。

注意

想在 Java 中构建 MCP stdio 服务器？ 服务器实现位于 LangChain4j Community 中。请参阅构建 Java MCP stdio 服务器 (opens new window)。

该协议指定了两种传输类型，LangChain4j 均支持：

  • Streamable HTTP (opens new window)： 客户端发送 HTTP 请求，服务器要么以常规响应回复，要么在需要随时间发送多个响应时打开 SSE 流。
  • stdio (opens new window)：客户端 可将 MCP 服务器作为本地子进程运行，并通过标准输入/输出直接与其通信。

在规范之上，LangChain4j 还实现了 WebSocket 传输。该传输尚未标准化，目前客户端的实现方式与 Quarkus MCP Server 扩展 (opens new window) 所实现的 WebSocket 传输兼容。对于使用其他框架构建但暴露 WebSocket 的 MCP 服务器，不保证兼容。

此外，LangChain4J 还支持 Docker stdio 传输，可使用以容器镜像形式分发的 stdio MCP 服务器。

LangChain4j 还支持旧版 HTTP/SSE 传输 (opens new window)， 但该方式已弃用，未来将被移除。

若要让聊天模型或 AI 服务运行 MCP 服务器提供的工具， 你需要创建一个 MCP 工具提供者（tool provider）实例。

# 创建 MCP 工具提供者

# MCP 传输

首先，你需要一个 MCP 传输（Transport）实例。

对于 stdio——以下示例展示如何从 NPM 包启动服务器作为子进程：

McpTransport transport = StdioMcpTransport.builder()
    .command(List.of("/usr/bin/npm", "exec", "@modelcontextprotocol/server-everything@0.6.2"))
    .logEvents(true) // only if you want to see the traffic in the log
    .build();

        .logRequests(true) // if you want to see the traffic in the log
        .logResponses(true)
        .build();

注意

Streamable HTTP 传输可选地打开附属 基于 GET 的 SSE 流 (opens new window)， 用于接收服务器发起的通知和请求。在 builder 上使用 .subsidiaryChannel(true) 启用。 默认禁用。若服务器不支持，传输会记录警告并继续运行。若流在建立后中断，传输会自动重连（遵循服务器的 retry 值，默认 5 秒）。

        .logResponses(true)
        .logRequests(true)
        .build();

从传输创建 MCP 客户端：

McpClient mcpClient = DefaultMcpClient.builder()
    .key("MyMCPClient")
    .transport(transport)
    .build();

请注意，客户端 key 是可选的，但建议设置，尤其是 存在多个 MCP 客户端、需要在它们之间区分时。

# MCP 工具提供者

最后，从客户端创建 MCP 工具提供者：

McpToolProvider toolProvider = McpToolProvider.builder()
    .mcpClients(mcpClient)
    .build();
1
2
3

请注意，一个 MCP 工具提供者可以同时使用多个客户端。 若利用这一点，你还可以指定当从某个特定服务器检索工具失败时工具提供者的行为——通过 builder.failIfOneServerFails(boolean) 方法完成。默认值为 false， 即工具提供者会忽略来自某一服务器的错误并继续处理其他服务器。若设为 true， 任一服务器的失败都会导致工具提供者抛出异常。

此外，MCP 服务器可能提供数十个工具，而给定的 AI 服务可能只需要其中少数几个——既是为了防止使用不想要的工具，也是为了 减少幻觉的可能性。McpToolProvider 允许按名称过滤 这些工具，如下所示：

McpToolProvider toolProvider = McpToolProvider.builder()
    .mcpClients(mcpClient)
    .filterToolNames("get_issue", "get_issue_comments", "list_issues")
    .build();
1
2
3
4

这样，配置了该 ToolProvider 的 AI 服务只能使用 上述 3 个工具，允许它读取现有 issue，但阻止它 创建新 issue。更一般地，ToolProvider 允许通过 BiPredicate<McpClient, ToolSpecification> 过滤工具。当多个 MCP 客户端暴露同名且 冲突的工具时，这也很有用。 例如，以下 ToolProvider 从两个 MCP 客户端获取工具， 但由于它们都有名为 echoInteger 的工具，它只采用 key 为 numeric-mcp 的 MCP 客户端提供的那个：

McpToolProvider toolProvider = McpToolProvider.builder()
    .mcpClients(mcpClient1, mcpClient2)
    .filter((mcpClient, tool) ->
            !tool.name().startsWith("echoInteger") || 
            mcpClient.key().equals("numeric-mcp"))
    .build();

4
5
6

请注意，在同一 McpToolProvider builder 上多次调用 filter 方法，将导致所有这些过滤器的合取（AND）。

为了允许应用在运行时连接或断开 MCP 服务器， 还可以动态地向现有 McpToolProvider 实例添加和移除客户端及过滤器。

要将工具提供者绑定到 AI 服务，只需在 AI 服务 builder 上使用 toolProvider 方法：

Bot bot = AiServices.builder(Bot.class)
    .chatModel(model)
    .toolProvider(toolProvider)
    .build();

Map<ToolSpecification, ToolExecutor> tools = mcpClient.listTools().stream().collect(Collectors.toMap(

# MCP 工具名称映射

若使用多个 MCP 服务器，且它们暴露名称冲突的工具（或你只是想 调整不合适的名称），应用工具名称映射函数可能很有用。 这可以在创建 McpToolProvider 时通过指定 BiFunction<McpClient, ToolSpecification, String> 完成。

例如：

McpToolProvider toolProvider = McpToolProvider.builder()
        .mcpClients(mcpClient1, mcpClient2)
        .toolNameMapper((client, toolSpec) -> {
            // Prefix all tool names with the name of the MCP client and an underscore
            return client.key() + "_" + toolSpec.name();
        })
        .build();
1
2
3
4
5
6
7

此后，工具提供者返回的 ToolSpecification 对象将包含映射后的（逻辑）名称， 但生成的 ToolExecutor 对象在调用工具时会固定向服务器传递原始（物理）名称。

# MCP 工具规范映射

与上述 MCP 工具映射类似，可以映射完整的 ToolSpecification：

McpToolProvider toolProvider = McpToolProvider.builder()
        .mcpClients(mcpClient)
        .toolSpecificationMapper((client, toolSpec) -> {
            // Prefix all tool names with "myprefix_" and convert the description to uppercase
            return toolSpec.toBuilder()
                .name("myprefix_" + toolSpec.name())
                .description(toolSpec.description().toUpperCase())
                .build();
        })
        .build();

# MCP 工具元数据

MCP 协议允许服务器以注解形式或在工具定义的 _meta 字段中为每个工具提供额外元数据。 LangChain4j 通过 ToolSpecification.metadata() 方法内存储的 map 暴露所有这些元数据。 注解使用可在 dev.langchain4j.mcp.client.McpToolMetadataKeys 类中找到的 常量作为 key 存储在 map 中。 _meta 字段的内容使用其原始 key 存储，JSON 值序列化为 嵌套 map。

MCP 工具定义中直接存在的 title 字段在元数据 map 的 McpToolMetadataKeys.TITLE key 下暴露，以区别于从注解检索的 title——后者在 McpToolMetadataKeys.ANNOTATION_TITLE key 下暴露。

若工具有图标，它们在元数据 map 的 McpToolMetadataKeys.ICONS key 下暴露。

# 提供 _meta 字段

MCP 协议允许客户端在发送给服务器的每个请求和通知的 params 中附加 _meta 对象。这可用于传递 OpenTelemetry 追踪上下文、自定义应用元数据，或服务器可能需要的任何其他 带外信息。

要提供 _meta 字段，在客户端 builder 上注册 McpMetaSupplier。 该 supplier 在每次请求或通知之前被调用，返回的 map 被放入 params._meta。与 HTTP 头不同，这在 所有传输（stdio、HTTP、WebSocket）上均有效。

McpClient mcpClient = DefaultMcpClient.builder()
    .transport(transport)
    .metaSupplier(context -> Map.of(
        "traceparent", "00-0af7651916cd43dd8448eb211c80319c-00f067aa0ba902b7-01",
        "custom-key", "custom-value"))
    .build();
1
2
3
4
5
6

supplier 接收 McpCallContext（可为 null），其中包含 正在发送的消息，以及（如适用）触发该调用的 AI 服务调用的 InvocationContext。这允许 supplier 根据 正在执行的操作变化元数据。

# 日志

MCP 协议还定义了服务器向 客户端发送日志消息的方式。默认情况下，客户端的行为是将这些日志 消息转换并使用 SLF4J 记录器记录。若要更改此 行为，有一个名为 dev.langchain4j.mcp.client.logging.McpLogMessageHandler 的接口，作为 接收到的日志消息的回调。若创建自己的 McpLogMessageHandler 实现，将其传递给 MCP 客户端 builder：

McpClient mcpClient = new DefaultMcpClient.Builder()
    .transport(transport)
    .logMessageHandler(new MyLogMessageHandler())
    .build();

# MCP 监听器

MCP 客户端支持监听器，可在 客户端生命周期内监听事件。接口 dev.langchain4j.mcp.client.McpClientListener 是 监听器实现的基类。可在 单个客户端上注册多个监听器；它们都会在每次 工具调用、提示渲染和资源访问之前和之后被调用。相应的 McpCallContext 在调用监听器时注入。该对象 包含实际发送给服务器的 MCP 消息，以及 （如适用）InvocationContext 实例（仅当此 调用作为 AI 服务调用的一部分发生时）。

监听器可以逐个添加或批量添加：

McpClient mcpClient = DefaultMcpClient.builder()
    .transport(transport)
    .addListener(new MyFirstListener())
    .addListener(new MySecondListener())
    .addListeners(List.of(new MyThirdListener(), new MyFourthListener()))
    .build();

# 资源

有两种方式处理资源。应用可以调用 MCP 客户端的 资源相关方法以编程方式访问资源，或者可以通过合成工具（一个用于获取资源列表、 一个用于获取资源内容）自动将资源暴露给 LLM 调用，以便聊天模型自行查阅资源。

# 以编程方式访问资源

要获取服务器上的 MCP 资源 (opens new window) 列表，使用 client.listResources()，或对于资源模板使用 client.listResourceTemplates()。 这将返回 McpResource 对象（或分别为 McpResourceTemplate）列表。这些 包含资源的元数据，最重要的是 URI。

要获取资源的实际内容，使用 client.readResource(uri)，提供资源的 URI。 这返回 McpReadResourceResult，其中包含 McpResourceContents 对象列表（单个 URI 上可能有多个资源内容，例如 若 URI 表示目录）。每个 McpResourceContents 对象表示 二进制 blob（McpBlobResourceContents）或文本（McpTextResourceContents）。

# 通过合成工具自动暴露资源

若在构建 McpToolProvider 时在 builder 上设置 McpResourcesAsToolsPresenter 实例， MCP 工具提供者会自动向其 provideTools 方法的结果添加两个合成工具， 与 backing MCP 服务器支持的「常规」工具一起。一个工具用于获取 资源列表，另一个用于获取特定资源。LangChain4j 提供 名为 DefaultMcpResourcesAsToolsPresenter 的默认实现，添加这两个工具：

注意

本节其余部分描述 DefaultMcpResourcesAsToolsPresenter。你可以插入行为不同的自定义实现。

  • list_resources：列出 backing MCP 服务器暴露的所有资源。该工具不接受参数。
  • get_resource：读取资源内容。该工具接受两个参数，共同标识一个资源： MCP 服务器名称和 URI。

list_resources 的输出是一个 JSON 数组，例如：

}, {
  "mcpServer" : "bob",
  "uri" : "file:///info",
  "uriTemplate" : null,
  "name" : "basicInfo",
  "description" : "Basic information about Bob",
  "mimeType" : "text/plain"
} ]

该数组中的每个文档代表一个资源。每个资源由 uri 和 mcpServer 的组合标识， 其中 mcpServer 是创建 MCP 客户端时分配的 key 值（见 DefaultMcpClient.Builder#key）。 当聊天模型调用 list_resources 工具时， 它接收此资源列表，然后可以决定调用 read_resource。在大多数情况下，list_resources 和 get_resource 工具的默认描述足以向 LLM 解释如何使用它们。但是，若需要 自定义这些工具及其参数的描述，可以使用 DefaultMcpResourcesAsToolsPresenter.Builder 的方法覆盖它们。

# 资源订阅

MCP 协议支持资源订阅 (opens new window)， 允许客户端在服务器上的资源发生变化时收到通知。

要订阅特定资源的更新，使用 client.subscribeToResource(uri)。 当服务器更新资源时，它发送 notifications/resources/updated 通知。 要处理这些通知，通过 onResourceUpdated builder 方法注册回调：

McpClient mcpClient = DefaultMcpClient.builder()
    .transport(transport)
    .onResourceUpdated((client, uri) -> {
        // re-read the updated resource
        McpReadResourceResult result = client.readResource(uri);
        // process the updated contents...
    })
    .build();

// subscribe to a resource
mcpClient.subscribeToResource("file:///status");

// later, unsubscribe
mcpClient.unsubscribeFromResource("file:///status");

# 提示（Prompts）

要获取服务器上的 MCP 提示 (opens new window) 列表，使用 client.listPrompts()。该方法返回 McpPrompt 列表。McpPrompt 包含提示的名称和参数信息。

要渲染提示的实际内容，使用 client.getPrompt(name, arguments)。渲染后的提示可包含一条到多条 消息，这些消息表示为 McpPromptMessage 对象。每个 McpPromptMessage 包含消息的角色（user、assistant 等） 和消息的实际内容。目前支持的消息内容类型 为：McpTextContent、McpImageContent 和 McpEmbeddedResource。

你可以使用 McpPromptMessage.toChatMessage() 将其转换为 LangChain4j 核心 API 的通用 dev.langchain4j.data.message.ChatMessage。 但并非所有情况都能转换。例如，若提示消息的 role 为 assistant 且包含文本以外的内容，将抛出异常。无论角色如何，将 包含二进制 blob 内容的消息转换为 ChatMessage 均不支持。

# 通过 Docker 使用 GitHub MCP 服务器

现在让我们看看如何使用 Model Context Protocol（MCP）以标准化方式将 AI 模型与外部工具桥接。 以下示例将通过 LangChain4j MCP 客户端与 GitHub 交互，获取并汇总公共 GitHub 仓库的最新提交。 为此无需重新发明轮子，我们可以使用 MCP GitHub 仓库 (opens new window) 中现有的 GitHub MCP 服务器实现 (opens new window)。

思路是构建一个 Java 应用，连接到本地 Docker 中运行的 GitHub MCP 服务器，以获取并汇总最新提交。 该示例使用 MCP 的 stdio 传输机制在我们的 Java 应用与 GitHub MCP 服务器之间通信。

# 在 Docker 中打包并运行 GitHub MCP 服务器

要与 GitHub 交互，首先需要在 Docker 中设置 GitHub MCP 服务器。 GitHub MCP 服务器提供通过 Model Context Protocol 与 GitHub 交互的标准化接口。 它支持文件操作、仓库管理和搜索功能。

要构建 GitHub MCP 服务器的 Docker 镜像，需要从 MCP servers GitHub 仓库 (opens new window) 获取代码（克隆仓库或下载代码均可）。 然后，导航到根目录并执行以下 Docker 命令：

docker build -t mcp/github -f src/github/Dockerfile .
1

Dockerfile 设置必要的环境并安装 GitHub MCP 服务器实现。 构建完成后，镜像将在本地以 mcp/github 可用。

# 开发工具提供者

让我们创建一个名为 McpGithubToolsExample 的 Java 类，使用 LangChain4j 连接 GitHub MCP 服务器。该类将：

  • 在 Docker 容器中启动 GitHub MCP 服务器（docker 命令位于 /usr/local/bin/docker）
  • 使用 stdio 传输建立连接
  • 使用 LLM 汇总 LangChain4j GitHub 仓库的最后 3 次提交

注意

在下面的代码中，我们通过环境变量 GITHUB_PERSONAL_ACCESS_TOKEN 传递 GitHub token。但对于某些不需要认证的公共仓库操作，这是可选的。

实现如下：

public static void main(String[] args) throws Exception {

    ChatModel model = OpenAiChatModel.builder()
        .apiKey(System.getenv("OPENAI_API_KEY"))
        .modelName("gpt-4o-mini")
        .logRequests(true)
        .logResponses(true)
        .build();

    McpTransport transport = new StdioMcpTransport.Builder()
        .command(List.of("/usr/local/bin/docker", "run", "-e", "GITHUB_PERSONAL_ACCESS_TOKEN", "-i", "mcp/github"))
        .logEvents(true)
        .build();

    McpClient mcpClient = new DefaultMcpClient.Builder()
        .transport(transport)
        .build();

    ToolProvider toolProvider = McpToolProvider.builder()
        .mcpClients(List.of(mcpClient))
        .build();

    Bot bot = AiServices.builder(Bot.class)
        .chatModel(model)
        .toolProvider(toolProvider)
        .build();

    try {
        String response = bot.chat("Summarize the last 3 commits of the LangChain4j GitHub repository");
        System.out.println("RESPONSE: " + response);
    } finally {
        mcpClient.close();
    }
}

# 不使用 AI 服务时使用 MCP

前面的示例展示了如何与高层 AI 服务 API 一起使用 MCP。但是，也可以通过低层 API 使用 MCP。 你可以手动使用构建的 DefaultMcpClient 实例对服务器执行命令。一些示例：

// obtain a list of tools from the server
List<ToolSpecification> toolSpecifications = mcpClient.listTools();

// build and execute a ChatRequest that has access to the MCP tools
ChatRequest chatRequest = ChatRequest.builder()
        .messages(UserMessage.from("What will the weather be like in London tomorrow?"))
        .toolSpecifications(toolSpecifications)
        .build();
ChatResponse response = chatModel.chat(chatRequest);
AiMessage aiMessage = response.aiMessage();

// if the LLM requested to invoke a tool, forward it to the MCP server
if(aiMessage.hasToolExecutionRequests()) {
    for (ToolExecutionRequest req : aiMessage.toolExecutionRequests()) {
        String resultString = mcpClient.executeTool(req);
        // prepare the result for adding it to the memory for the next ChatRequest...
        ToolExecutionResultMessage resultMessage = ToolExecutionResultMessage.from(req.id(), req.name(), resultString);
    }
}

# 关于工具缓存的说明

DefaultMcpClient 维护 MCP 工具的内部缓存。一旦检索后，工具列表 不会再次向 MCP 服务器请求，除非服务器发送 工具列表已更新的通知。你可以通过调用 DefaultMcpClient.evictToolListCache() 手动清除此缓存。 若希望完全禁用缓存，按如下方式配置客户端：

McpClient mcpClient = new DefaultMcpClient.Builder()
    .key("MyMCPClient")
    .transport(transport)
    .cacheToolList(false)
    .build();

# MCP Registry 客户端

LangChain4j 还提供单独的客户端实现，可与 MCP 注册表 (opens new window) 通信。目前仅 实现了只读操作（你可以搜索 MCP 服务器，但不支持管理和添加服务器——请使用 官方工具 (opens new window) 完成）。

警告

发现 MCP 服务器并使用它们（尤其是在本地运行）可能带来严重的安全风险。在 运行你在公共注册表中找到的任何 MCP 服务器之前，请确保你可以信任它。

注册表客户端 位于 dev.langchain4j.mcp.registryclient 包中，可按如下方式初始化：

McpRegistryClient client = DefaultMcpRegistryClient.builder()
        .baseUrl("URL-OF-THE-REGISTRY")
        .build();
1
2
3

若未提供 base URL，默认使用官方注册表（https://registry.modelcontextprotocol.io）。 然后，要搜索 MCP 服务器，使用 registry.listServers(McpServerListRequest) 方法。McpServerListRequest 对象可使用 McpServerListRequest.Builder 类构建。LangChain4j 中的 Java API 与官方 MCP Registry Reference (opens new window) 中描述的 MCP 注册表 REST API 紧密对应。
