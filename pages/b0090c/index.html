    # 基础概念

    # 什么是 MVCC？

    MVCC（Multi-Version Concurrency Control），即多版本并发控制，是一种数据库并发控制技术。它通过为数据维护多个版本，实现读写操作的无锁并发，提高数据库的并发性能。

    核心思想：

    • 为每一行数据维护多个版本
    • 读操作可以访问历史版本，无需等待写操作完成
    • 写操作创建新的版本，不影响读操作

    # 当前读与快照读

    在 InnoDB 中，查询操作分为两种类型：

    # 当前读（Current Read）

    • 定义：读取的是数据最新的、真实的当前版本，必须加锁，保证数据绝对最新
    • 底层原理：加 共享锁 / 排他锁，阻塞其他事务修改，强制读取最新数据。
    • 适用操作：
      • SELECT ... LOCK IN SHARE MODE（共享锁）
      • SELECT ... FOR UPDATE（排他锁）
      • UPDATE、INSERT、DELETE 相关操作（排他锁）

    例如:

    -- 1. 锁定读
SELECT * FROM user WHERE id = 1 FOR UPDATE;
SELECT * FROM user WHERE id = 1 LOCK IN SHARE MODE;

-- 2. 修改数据（底层都是先当前读，再修改）
UPDATE user SET name = "张三" WHERE id = 1;
DELETE FROM user WHERE id = 1;
INSERT INTO user ...;

    • 特点：保证数据一致性，但会阻塞其他事务的写操作

    # 快照读（Snapshot Read）

    • 定义：读取数据的历史版本，不加锁的非阻塞读
    • 适用操作：普通的 SELECT 语句（未加锁）
    • 特点：
      • 提高并发性能，不会阻塞其他事务
      • 可能读取到的不是最新版本的数据
      • 在串行隔离级别下会退化为当前读

    # MVCC 与读写冲突

    数据库并发场景：

    1. 读-读：无冲突，无需并发控制
    2. 读-写：可能导致脏读、不可重复读、幻读
    3. 写-写：可能导致更新丢失

    MVCC 的作用：

    • 专门解决 读-写冲突，实现读写操作的并行执行
    • 对于 写-写冲突，仍需要锁机制来解决(自己去决定当前的业务是使用悲观锁还是乐观锁去解决相关问题)

    # MVCC 的优势

    1. 提高并发性能：读写操作互不阻塞，同时执行
    2. 减少锁竞争：降低了锁的使用，减少了死锁的可能性
    3. 保证事务隔离：解决了脏读、不可重复读、幻读等问题
    4. 简化编程模型：应用程序无需关心复杂的锁机制

    MVCC 与锁的组合：

    • MVCC + 悲观锁：MVCC 解决读写冲突，悲观锁解决写写冲突
    • MVCC + 乐观锁：MVCC 解决读写冲突，乐观锁解决写写冲突

    # 悲观锁 vs 乐观锁 场景对比表

    对比项 悲观锁（Pessimistic Lock） 乐观锁（Optimistic Lock）
    核心思想 默认并发一定会发生冲突，访问数据前先上锁，锁住资源，其他线程阻塞等待 默认并发极少冲突，不加物理锁，更新时校验版本，冲突则重试/回滚
    底层实现 数据库：select ... for update（行锁/表锁）、数据库行级排他锁；
    Java：synchronized、ReentrantLock    		 数据库：版本号version、时间戳timestamp；
    CAS自旋（Redis、Java原子类）
    加锁时机 查询/读取数据时直接加锁，占用资源直至事务提交 读不加锁，只有更新时校验锁标识
    并发冲突处理 冲突线程阻塞排队，等待锁释放 冲突直接失败，业务重试、抛出异常
    性能表现 并发量大时阻塞严重、吞吐量低；锁占用CPU/数据库连接 无阻塞，高并发吞吐更高；频繁冲突场景大量重试损耗性能
    ✅适用场景 1. 写多读少，更新频繁、竞争激烈；
    2. 数据一致性要求极高，不允许脏数据；
    3. 短事务（锁持有时间短）；
    4. 金融扣款、库存扣减（超高竞争）    		 1. 读多写少，查询远大于修改；
    2. 并发冲突概率低；
    3. 长事务（锁占用时间长，悲观锁会长期占资源）；
    4. 电商商品详情、用户基础信息修改
    典型业务案例 银行转账扣款、库存秒杀（超高并发扣库存）、订单状态强一致性变更 商品价格修改、用户资料更新、订单备注修改、积分少量变动
    主要弊端 死锁风险、连接耗尽、高并发下性能雪崩 频繁冲突时无限自旋/大量重试，CPU飙升；无法解决ABA问题（CAS）

    # MVCC 实现原理

    MVCC 的实现依赖于以下三个核心组件：

    • 隐式字段：记录数据的版本信息，标记「这个版本是谁写的、上一版在哪」
    • Undo 日志：存储数据的历史版本，串成版本链
    • Read View：判断数据可见性的规则,快照读时判断「这个版本对我是否可见」

    # 隐式字段

    InnoDB 为每行数据添加了三个隐藏字段：

    字段名 大小 作用
    DB_ROW_ID 6字节 隐含的自增ID（隐藏主键），当表没有主键时自动生成
    DB_TRX_ID 6字节 记录创建或最后修改该记录的事务ID
    DB_ROLL_PTR 7字节 回滚指针，指向该记录的上一个版本（存储在 Undo 日志中）
    DELETED_BIT 1字节 标记记录是否被删除（逻辑删除） 删除标记一般是记录头里的删除标志位（逻辑删除），不是和上面三个并列的

    DB_TRX_ID 是 InnoDB 为每个行版本记录的「最后修改该版本的事务 id」（6 字节）。

    • 全局 trx_id 由 InnoDB trx_sys 单调分配；写事务（或需要 trx_id 的锁读）在首次需要时领取，不是每次 BEGIN 都 +1。
    • 实例重启后从持久化状态继续递增，不回到 1；上限为 2^48 - 1。ps:因为 DB_TRX_ID 是 6 字节（48 位）的无符号整数，所以最大值就是 2⁴⁸ - 1。2⁴⁸−1 是行上 DB_TRX_ID 的硬上限；trx_id 用掉不回收，生产上几乎不可能耗尽。若真耗尽，InnoDB 没有安全的 ID 回绕或在线重置——会继续发号但落盘截断，MVCC 可能错乱，只能按 corruption(数据损坏) 思路逻辑备份后重建实例。
    • 快照读通过 Read View 与行上的 DB_TRX_ID 比较，不可见则沿 DB_ROLL_PTR → undo 版本链 找历史版本。

    # Undo 日志

    Undo 日志是 InnoDB 用来实现事务回滚和 MVCC 的重要机制，它记录了数据的历史版本。

    # Undo 日志类型：

    1. Insert Undo Log：记录插入操作，事务回滚时删除对应记录
    2. Update Undo Log：记录更新操作，事务回滚时恢复旧值
    3. Delete Undo Log：记录删除操作，事务回滚时重新插入记录

    注意：删除操作只是设置 DELETED_BIT 标记，并不真正删除数据。InnoDB 有专门的 purge 线程负责清理已标记为删除的记录。

    # Undo 日志的工作流程：

    1. 初始状态：插入一条新记录，事务ID和回滚指针为 NULL

    2. 事务1修改：将 name 改为 Tom

      • 对记录加排他锁
      • 将旧记录拷贝到 Undo 日志
      • 修改记录，更新事务ID为1，回滚指针指向 Undo 日志中的旧记录
      • 提交事务，释放锁

    3. 事务2修改：将 age 改为 30

      • 对记录加排他锁
      • 将当前记录（Tom, 24）拷贝到 Undo 日志，作为链表的新表头
      • 修改记录，更新事务ID为2，回滚指针指向新的 Undo 日志记录
      • 提交事务，释放锁

    这样，Undo 日志就形成了一条版本链，链首是最新的旧版本，链尾是最早的旧版本。

    # Read View（读视图）

    Read View 是事务执行快照读时生成的一个数据结构，用于判断当前事务能够看到哪个版本的数据。

    # Read View 核心字段

    字段 含义（快照建立那一刻）
    up_limit_id 活跃事务中最小的事务ID :严格小于它的 trx_id，视为在快照前已结束/一定可见（对非本事务）
    low_limit_id 系统下一个要分配的事务ID（即当前最大事务ID+1）：大于等于它的 trx_id，视为快照之后才出现，一定不可见
    trx_list 活跃事务 ID 列表:建立快照时仍活跃的读写事务 id 列表（有序，二分查找）
    m_creator_trx_id 创建该 Read View 的当前事务 id（自己的修改要可见）
    m_low_limit_no 给 purge 用，判断 undo 能否清理；不参与 changes_visible 与 DB_TRX_ID 的比较

    # 可见性判断规则：

    1. 如果 DB_TRX_ID < up_limit_id：

      • 说明修改该记录的事务在当前事务开始前已提交，可见

    2. 否则，如果 DB_TRX_ID >= low_limit_id：

      • 说明修改该记录的事务在当前事务开始后才启动，不可见

    3. 否则，如果 DB_TRX_ID 在 trx_list 中：

      • 说明修改该记录的事务当前仍活跃，不可见

    4. 否则：

      • 说明修改该记录的事务在当前事务开始前已提交，可见

    设当前版本行的 DB_TRX_ID = id，按顺序判断：

    ① id < up_limit_id  → 可见
② id == creator_trx_id → 可见（自己改的）
③ id >= low_limit_id → 不可见
④ id 在 ids 里（二分查找命中）→ 不可见（快照时还在跑）
⑤ 否则 → 可见（创建快照时已提交、且不在活跃列表里）

    # 整体工作流程

    # 案例一：事务2 的快照读（链头可见，直接返回）

    场景：

    • 事务1：活跃中，尚未提交，事务 id=1
    • 事务2：执行快照读，事务 id=2
    • 事务3：活跃中，尚未提交，事务 id=3
    • 事务4：已提交（修改过数据），事务 id=4

    Read View 生成（事务2 执行 SELECT 时创建）：

    • trx_list = [1, 3]（活跃读写事务，不含 creator 事务2）
    • up_limit_id = 1
    • low_limit_id = 5（4+1）
    • m_creator_trx_id = 2

    数据版本链（此时聚簇索引链头仍是事务4 的版本）：

    完整流程：

    步骤 动作
    1 事务2 执行普通 SELECT，InnoDB 为事务2 创建 Read View
    2 按索引定位到该行，取聚簇索引链头，DB_TRX_ID = 4
    3 用 Read View 做可见性判断（①～⑤）
    4 4 不在 trx_list 中，且不满足不可见条件 → 可见
    5 直接返回该版本，无需回溯 undo

    可见性判断（链头 DB_TRX_ID = 4）：

    1. 4 < 1？否
    2. 4 == 2（creator_trx_id）？否
    3. 4 >= 5？否
    4. 4 在 [1, 3] 中？否
    5. 结论：可见

    结果：事务2 读到事务4 提交的版本（例如 age = 25）。

    # 案例二：事务3 的快照读（链头不可见，沿 undo 回溯）

    场景（接案例一之后）：

    • 事务1：仍活跃，尚未提交，事务 id=1
    • 事务2：执行 UPDATE 将 age 改为 28，尚未提交，事务 id=2
    • 事务3：此刻执行快照读，事务 id=3
    • 事务4：早已提交，事务 id=4（上一版 age = 25）

    版本链（事务2 写入后，链头已变）：

    聚簇索引 → [trx_id=2, name=Tom, age=28]   ← 事务2 未提交（链头）
              ↓ DB_ROLL_PTR
           [trx_id=4, name=Tom, age=25]   ← 事务4 已提交
    1
    2
    3

    Read View 生成（事务3 执行 SELECT 时创建，与事务2 的 Read View 相互独立）：

    • trx_list = [1, 2]（活跃读写事务，不含 creator 事务3；事务2 在列表中，事务3 不在）
    • up_limit_id = 1
    • low_limit_id = 5
    • m_creator_trx_id = 3

    完整流程：

    步骤 动作
    1 事务3 执行普通 SELECT，InnoDB 为事务3 新建 Read View
    2 定位到该行，取聚簇索引链头，DB_TRX_ID = 2
    3 第 1 轮可见性判断 → 不可见（事务2 仍在 trx_list 中）
    4 沿 DB_ROLL_PTR 读 undo，还原上一版，DB_TRX_ID = 4
    5 第 2 轮可见性判断 → 可见
    6 返回 age = 25，跳过事务2 未提交的 age = 28

    第 1 轮：链头 trx_id = 2

    1. 2 < 1？否
    2. 2 == 3（creator_trx_id）？否
    3. 2 >= 5？否
    4. 2 在 [1, 2] 中？是 → 不可见

    → 沿 DB_ROLL_PTR 进入 undo，取上一版。

    第 2 轮：trx_id = 4

    1. 4 < 1？否
    2. 4 == 3？否
    3. 4 >= 5？否
    4. 4 在 [1, 2] 中？否
    5. 可见

    结果：事务3 读到 age = 25（事务4 的版本），看不到事务2 未提交的 age = 28。

    与案例一对比：

    对比项 案例一（事务2 读） 案例二（事务3 读）
    Read View 创建者 事务2 事务3
    trx_list [1, 3] [1, 2]
    链头 DB_TRX_ID 4（已提交） 2（未提交）
    是否回溯 undo 否 是（1 次）
    最终读到的 age 25 25

    两个事务各自拍快照、各自判断；事务3 晚来一步，链头已被事务2 改掉，但通过回溯仍读到已提交的旧版本，避免脏读。

    ps:在真实场景若是纯快照读，案例1中的事务 2、案例2中的事务3 可能没有 trx_id，但 Read View 和可见性判断照样进行。只是 creator_trx_id = 0。

    # 不可见时怎么办？——沿 Undo 版本链回溯

    快照读不会因为当前版本不可见就失败（案例二已完整演示），通用流程如下：

    1. 从聚簇索引取出当前行（版本链链头）；
    2. 用 Read View 对 DB_TRX_ID 做 changes_visible 判断；
    3. 可见 → 直接返回该版本；
    4. 不可见 → 沿 DB_ROLL_PTR 读 Undo 日志，还原上一版，对其 DB_TRX_ID 重复步骤 2；
    5. 直到找到第一个可见版本，或链到头仍不可见（视为该行对当前事务不存在，例如已被删除且对快照不可见）。
    聚簇索引（链头） → 判可见性
       ↓ 不可见
   Undo 上一版   → 再判可见性
       ↓ 不可见
      ...        → 继续回溯
       ↓ 可见
   返回该历史版本给 SELECT

    # MVCC 与事务隔离级别

    # RC 与 RR 级别的区别

    MVCC 在不同事务隔离级别下的行为不同，主要体现在 Read View 的生成时机 上：

    隔离级别 Read View 生成时机 特点
    READ COMMITTED (RC) 当前事务中，每次快照读都会生成新的 Read View 可以看到其他事务已提交的修改
    REPEATABLE READ (RR) 在当前事务中 事务中第一次快照读时生成 Read View，之后复用 只能看到事务开始时的数据状态

    # 不可重复读的解决原理

    不可重复读：同一事务中多次读取同一数据，得到不同结果。

    RR 级别如何解决不可重复读：

    • 事务开始后第一次快照读会生成 Read View
    • 该 Read View 记录了当时系统中活跃的事务
    • 后续所有快照读都使用同一个 Read View
    • 即使其他事务提交了修改，由于 Read View 未变，仍然看不到这些修改

    示例：

    • RR 级别下，事务中第一次快照读的时机非常重要，它决定了整个事务能看到的数据版本
    • 如果第一次快照读在其他事务修改之前，后续快照读将看不到这些修改
    • 如果第一次快照读在其他事务修改之后，就能看到这些已提交的修改

    # MVCC 最佳实践

    1. 合理选择隔离级别：

      • 一般情况下使用 REPEATABLE READ (RR) 级别，保证数据一致性
      • 对于需要实时数据的场景，可使用 READ COMMITTED (RC) 级别

    2. 优化 Undo 日志：

      • 合理设置 innodb_undo_logs 参数
      • 监控 Undo 日志大小，避免过度增长

    3. 避免长事务：

      • 长事务会持有 Read View 更长时间
      • 导致 Undo 日志无法被及时清理，占用更多空间

    4. 使用合适的索引：

      • 索引可以减少 MVCC 中版本链的遍历时间
      • 提高快照读的性能

    # 常见问题与解答

    # 1. MVCC 会影响数据库性能吗？

    影响有限：MVCC 通过版本链和 Read View 实现，会增加一些存储和计算开销，但这些开销远小于锁竞争带来的性能损失。

    # 2. MVCC 能解决所有并发问题吗？

    不能：MVCC 主要解决读-写冲突，对于写-写冲突仍需要锁机制来解决。

    # 3. Undo 日志会无限增长吗？

    不会：InnoDB 有 purge 线程定期清理不再需要的 Undo 日志。但长事务会延迟 Undo 日志的清理。

    # 4. 为什么有时快照读会读到旧数据？

    正常现象：这是 MVCC 的设计目的，保证事务隔离性。如果需要最新数据，应使用当前读（加锁读）。

    # 相关技术：InnoDB 日志体系

    本文重点讲了 MVCC 如何通过 Undo 日志 + Read View 实现多版本读，但 InnoDB 事务的完整实现还依赖 Buffer Pool、Redo Log、Binlog 等机制。其中 Buffer Pool 是所有读写操作的「主战场」——MVCC 的版本链、Read View 判断、redo/undo 的产生，都发生在 Buffer Pool 中的数据页上。

    # Buffer Pool（缓冲池）

    Buffer Pool 是 InnoDB 最大、最核心的内存结构，用于在内存中缓存数据页和索引页，减少磁盘 I/O，提高读写性能。

    # 为什么需要 Buffer Pool？

    磁盘读写远慢于内存。如果每次 SELECT / UPDATE 都直接读写在磁盘上，数据库性能无法接受。InnoDB 的做法是：

    把磁盘上的页加载到内存，后续访问优先在内存中完成；修改也先在内存中进行，再异步刷回磁盘。

    本文中提到的聚簇索引行、DB_TRX_ID、DB_ROLL_PTR，以及快照读时的可见性判断，实际都发生在 Buffer Pool 里已加载的数据页上。

    # 页（Page）—— Buffer Pool 的管理单位

    InnoDB 不以「行」为单位管理内存，而是以 页 为单位（默认 16KB，innodb_page_size）：

    页类型 说明
    数据页 存储表行数据（聚簇索引页）
    索引页 存储二级索引的 B+ 树节点
    Undo 页 存储 undo 记录（访问时也会载入 Buffer Pool）
    系统页 数据字典、事务系统等元数据

    一行数据只占页的一部分；加载一行时，InnoDB 会把整页读入 Buffer Pool。

    # 干净页 vs 脏页

    状态 含义
    干净页（Clean Page） 内存中的内容与磁盘一致
    脏页（Dirty Page） 内存中已修改，但尚未刷回磁盘

    脏页刷盘由 Page Cleaner Thread 等后台线程负责，触发时机包括：

    • Buffer Pool 空间不足，LRU 淘汰页时需要刷脏页
    • Redo Log 快写满，需要推进 checkpoint
    • 脏页比例超过阈值（innodb_max_dirty_pages_pct）
    • 数据库正常关闭（shutdown）

    # LRU 管理与 young / old 区

    Buffer Pool 使用 改进的 LRU 算法管理页的换入换出，分为 young 区（热数据）和 old 区（冷数据）：

    ┌──────────────────────────────────────────┐
│  young 区（最近频繁访问的页，头部）         │
├──────────────────────────────────────────┤
│  old 区（新载入 / 较少访问的页，尾部）      │
└──────────────────────────────────────────┘
    1
    2
    3
    4
    5
    • 新读入的页先放到 old 区头部（midpoint insertion），而不是直接放到 LRU 头部
    • 页在 old 区被再次访问后，才晋升到 young 区
    • 目的：防止一次性全表扫描把热点数据挤出 Buffer Pool

    # 与 MVCC 的关系

    MVCC 环节 在 Buffer Pool 中的体现
    读链头版本 从聚簇索引数据页中取当前行
    可见性判断 读页内行的 DB_TRX_ID，与 Read View 比较
    回溯 undo 沿 DB_ROLL_PTR 读 undo 页中的历史版本，拼出旧行
    写新版本 在 Buffer Pool 的页内原地修改行，旧值写入 undo 页

    可以这么理解：MVCC 是逻辑机制，Buffer Pool 是物理载体。没有 Buffer Pool，每次版本链遍历都要读磁盘，MVCC 的性能优势会大打折扣。

    # 关键参数

    参数 作用 建议
    innodb_buffer_pool_size Buffer Pool 总大小 物理内存的 60%～75%（专用 DB 服务器）
    innodb_buffer_pool_instances 拆分为多个实例，减少锁竞争 大内存时可设为 8～64
    innodb_old_blocks_pct old 区占 LRU 的比例 默认 37，控制全表扫描影响范围
    innodb_max_dirty_pages_pct 脏页上限比例 默认 75，影响刷盘频率

    # Redo Log（重做日志）

    Redo Log 记录的是数据页被修改后的物理变更，用于保证已提交事务的修改在崩溃后仍可恢复。

    # 核心特点

    特点 说明
    物理日志 记录「哪个表空间、哪一页、偏移多少、改成了什么」
    WAL 机制 Write-Ahead Logging：先写 redo，再异步把 Buffer Pool 中的脏页刷回磁盘
    循环写入 固定大小文件（默认 ib_logfile0/1），写满后覆盖最旧的部分
    LSN Log Sequence Number，单调递增，标记 redo 写入进度和 checkpoint 位置

    # 为什么需要 Redo？

    InnoDB 的更新策略是：修改先发生在内存（Buffer Pool），脏页刷盘是异步的。如果数据库在脏页落盘前崩溃，内存中的修改会丢失。Redo Log 保证：

    只要 redo 已落盘，即使数据页还没刷盘，重启后也能通过 redo 前滚（replay） 把页恢复到一致状态。

    # 刷盘策略

    通过 innodb_flush_log_at_trx_commit 控制：

    值 行为 安全性 性能
    0 每秒刷盘 可能丢最多 1 秒 最快
    1 每次事务提交刷盘 最安全（生产推荐） 较慢
    2 提交时写 OS cache，每秒 fsync 折中 中等

    # Undo 与 Redo 的分工

    这是 InnoDB 日志体系里最经典的一句口诀：

    Undo 保证「能撤销、能读历史」；Redo 保证「已提交的不丢」。

    对比项 Undo Log Redo Log
    记录时机 修改之前，写旧值 修改同时，写页的物理变更
    记录内容 逻辑旧版本 物理页修改
    主要读者 快照读（MVCC）、ROLLBACK 崩溃恢复（crash recovery）
    生命周期 提交后进 History List，Purge 回收 循环覆盖，checkpoint 之后可覆盖
    本文角色 版本链的数据来源 保护版本链所在的数据页和 undo 页

    两者在每次写操作中同时产生：改一行数据时，先写 undo 记旧值，再改 Buffer Pool 中的页，同时写 redo 保护这次物理修改。

    # 案例：INSERT + UPDATE 看 Undo 与 Redo 各自记什么

    下面用一个具体例子，把两种日志各自落盘的内容说清楚。假设表 user 使用 InnoDB，包含隐式字段 DB_TRX_ID、DB_ROLL_PTR。

    -- 事务 T1
INSERT INTO user(name, age, sex) VALUES ('zhangsan', 15, 1);

-- 事务 T2（后续）
UPDATE user SET age = 16 WHERE name = 'zhangsan';

    1. 写 Insert Undo Log
2. 在聚簇索引页插入新行
3. 写 Redo Log（保护本次所有页的物理修改）
4. COMMIT

    Insert Undo Log 记什么？（逻辑，给回滚用）

    字段 示例内容 作用
    操作类型 INSERT 标识这是一条插入撤销记录
    表 ID user 表对应 id 定位哪张表
    主键值 id = 100 定位哪一行
    回滚语义 「删除主键 = 100 的记录」 T1 回滚时物理删除该行

    注意：Insert Undo 只服务于 ROLLBACK，不进入 MVCC 版本链——新插入的行没有「上一版本」，其他事务的快照读也看不到未提交的新行。

    Redo Log 记什么？（物理，给崩溃恢复用）

    Redo 不关心 zhangsan、15 这些业务语义，只记录 Buffer Pool 里哪些字节被改了：

    物理变更对象 示例内容
    聚簇索引数据页 表空间 X，页号 Y，偏移 Z 处写入新行：zhangsan, 15, 1, DB_TRX_ID=T1, DB_ROLL_PTR→Insert Undo
    二级索引页（如有） name 索引页插入对应条目
    Undo 页 Insert Undo 记录本身写入 undo 页的物理变更
    # 第二步：UPDATE（age: 15 → 16）

    执行顺序：

    1. 对目标行加锁
2. 写 Update Undo Log（拷贝旧行）
3. 在 Buffer Pool 中修改聚簇索引行
4. 写 Redo Log
5. COMMIT

    Update Undo Log 记什么？（逻辑，给回滚 + MVCC 用）

    字段 示例内容 作用
    操作类型 UPDATE 标识这是一条更新撤销记录
    旧行镜像 name=zhangsan, age=15, sex=1 回滚时恢复旧值
    事务 ID T2 标识这个版本由谁产生
    版本链指针 指向更早的 undo（若有） 串成 MVCC 版本链

    注意：Update Undo 既用于 ROLLBACK，也用于 MVCC。T2 未提交时，其他事务的快照读沿 DB_ROLL_PTR 回溯到此 undo，读到的仍是 age=15。

    Redo Log 记什么？（物理，给崩溃恢复用）

    物理变更对象 示例内容
    聚簇索引数据页 表空间 X，页号 Y，偏移 Z 处 age 字段：0x0F(15) → 0x10(16)
    隐式字段 DB_TRX_ID 更新为 T2；DB_ROLL_PTR 改为指向新 Update Undo
    Undo 页 Update Undo 记录写入 undo 页的物理变更

│ DB_ROLL_PTR ──────┐                 │
└───────────────────│─────────────────┘
                    ▼
              Update Undo（T2 写入）
              name=zhangsan, age=15, sex=1
                    │
                    ▼
              Insert Undo（T1，提交后通常已被 Purge 清理）

    # 两步操作汇总对比
    操作 Undo Log 具体记了什么 Redo Log 具体记了什么
    INSERT Insert Undo：主键 + 「回滚则删除该行」 数据页写入新行、索引页、undo 页的物理字节变更
    UPDATE Update Undo：旧行完整镜像 {age=15} 数据页 age 15→16、DB_TRX_ID/DB_ROLL_PTR、undo 页的物理字节变更
    # 不同读者各自用哪份日志？
    场景 使用的日志 读到什么
    T2 提交后的当前读 聚簇索引链头 age=16
    T2 开始前的快照读 Undo 版本链 age=15
    T2 执行中 ROLLBACK Update Undo 恢复 age=15
    数据库崩溃重启 Redo 前滚 恢复 age=16（已提交）
    崩溃时 T2 未提交 Redo + Undo Redo 恢复页后，Undo 回滚掉 T2 的修改
    # 一句话对照
    Undo 回答的是：「改之前长什么样？」→ 逻辑旧值，给人看（回滚 / 快照读）
Redo 回答的是：「页上哪些字节变了？」→ 物理修改，给机器做（崩溃恢复）

    # Binlog（二进制日志）

    Binlog 是 MySQL Server 层的日志，不属于某个存储引擎，所有引擎的变更都可以记录。

    对比项 Redo Log Binlog
    层级 InnoDB 引擎层 MySQL Server 层
    内容 物理页修改 逻辑变更（SQL 或行镜像）
    写入方式 循环写，固定大小 追加写，文件轮转
    主要用途 崩溃恢复 主从复制、增量备份、CDC
    是否必须 InnoDB 必有 可选（主从/备份场景必须开）

    格式（binlog_format）：

    格式 记录内容 特点
    STATEMENT 原始 SQL 日志小，但不确定函数可能导致主从不一致
    ROW 行变更前后镜像 准确，生产推荐
    MIXED 自动选择 折中

    刷盘策略由 sync_binlog 控制（0 / 1 / N），生产环境通常设为 1，与 innodb_flush_log_at_trx_commit = 1 配合使用。

    # 两阶段提交（2PC）

    当同时开启 redo 和 binlog 时，InnoDB 用两阶段提交保证两者一致，避免崩溃后主库与从库数据不同步。

    问题场景（若无 2PC）：

    崩溃时机 后果
    redo 已写、binlog 未写 主库恢复后有数据，从库 binlog 缺失 → 主从不一致
    binlog 已写、redo 未 commit 主库恢复后回滚，从库已回放 → 主从不一致

    2PC 流程：

    1. 写 redo log，标记为 prepare
2. 写 binlog
3. 写 redo log，标记为 commit

    3

    只有 redo 处于 commit 状态的事务，才视为真正提交成功。崩溃恢复时会检查 redo 与 binlog 的对应关系，决定提交还是回滚。

    # 一条 UPDATE 的完整日志链路

    以 UPDATE account SET amount = 400 WHERE id = 1 为例，把 MVCC 与三种日志串起来：

    1. 对目标行加锁（写-写冲突仍靠锁）
2. 写 Undo Log：拷贝旧值（amount=100）到 undo 页
3. 修改 Buffer Pool 中的聚簇索引行：
     - amount = 400
     - DB_TRX_ID = 当前事务 id
     - DB_ROLL_PTR → 指向刚写的 undo 记录
4. 写 Redo Log：记录数据页 + undo 页的物理修改
5. COMMIT：
     a. redo prepare
     b. 写 binlog（若开启）
     c. redo commit
6. 释放行锁

    # 崩溃恢复与 MVCC 的协同

    数据库崩溃重启后，InnoDB 的恢复流程大致为：

    1. Redo 前滚：从 checkpoint 起 replay redo，恢复 Buffer Pool 中未刷盘的已提交修改
2. Undo 回滚：扫描活跃事务列表，对未提交事务沿 undo 链反向撤销修改
3. 恢复正常服务：MVCC、Read View 机制继续工作
    1
    2
    3
    阶段 使用的日志 作用
    前滚 Redo 把已 prepare/commit 的物理修改重做
    回滚 Undo 撤销仍处于活跃状态的事务的修改
    正常运行 Undo + Read View MVCC 快照读继续沿版本链找可见版本

    已提交的事务不会被 undo 撤销——undo 在崩溃恢复中只处理「提交了 redo 但事务状态未完成」或「仍在活跃列表中」的情况。

    与本文的关联小结：

    • Buffer Pool 是 MVCC 读写的物理载体：聚簇索引行、版本链、Read View 判断都在内存页中完成
    • 本文讲的 MVCC 读路径：Read View → 聚簇索引链头 → 不可见则沿 Undo 版本链回溯
    • Redo 不参与可见性判断，但保证 Buffer Pool 中脏页和 undo 页在崩溃后可恢复
    • Binlog 不参与 MVCC，但保证变更可复制到其他节点
    • Purge 在 undo 不再需要时清理旧版本，与 Read View 的 m_low_limit_no 直接相关——这也是长事务导致 undo 膨胀的根本原因

    # 总结

    MVCC（多版本并发控制）是 InnoDB 存储引擎的核心特性，通过以下机制实现：

    1. 版本管理：通过隐式字段和 Undo 日志维护数据的多个版本
    2. 可见性判断：通过 Read View 决定事务能看到哪个版本的数据
    3. 隔离级别适配：根据不同隔离级别调整 Read View 的生成时机
    4. 内存缓存：Buffer Pool 在内存中缓存数据页，MVCC 读写实际在此完成
    5. 持久性保障：Redo Log（WAL）保证脏页在崩溃后可恢复；Binlog + 2PC 保证主从一致

    核心优势：

    • 实现读写操作的并行执行，提高并发性能
    • 减少锁竞争，降低死锁可能性
    • 保证事务隔离性，解决脏读、不可重复读、幻读问题

    应用建议：

    • 理解 MVCC 的工作原理，合理设计事务
    • 根据业务需求选择合适的隔离级别
    • 避免长事务，及时提交或回滚（长事务会拖慢 Purge、导致 Undo 膨胀）
    • 优化索引，提高 MVCC 操作效率
    • 生产环境关注 innodb_buffer_pool_size 配置，保证缓存命中率
    • 生产环境关注 innodb_flush_log_at_trx_commit 与 sync_binlog 的配置

    通过掌握 MVCC 及其配套的 Buffer Pool / Undo / Redo / Binlog 机制，你可以更好地理解 MySQL 的事务处理原理，从而编写更高效、更可靠的数据库应用。
