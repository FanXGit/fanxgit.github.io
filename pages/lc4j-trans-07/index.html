# 工具（函数调用）

除了生成文本之外，一些 LLM 还可以触发操作。

注意

所有支持工具的 LLM 可在此处 (opens new window)找到（参见「Tools」列）。

注意

并非所有 LLM 对工具的支持程度都相同。 理解、选择并正确使用工具的能力在很大程度上取决于具体模型及其能力。 有些模型可能完全不支持工具，而另一些模型可能需要仔细的提示工程 或额外的系统指令。

存在一种称为「工具（tools）」或「函数调用（function calling）」的概念。 它允许 LLM 在必要时调用一个或多个可用工具，这些工具通常由开发者定义。 工具可以是任何内容：网络搜索、对外部 API 的调用，或执行特定代码片段等。 LLM 实际上无法自行调用工具；相反，它们会在响应中表达 调用特定工具的意图（而不是以纯文本形式响应）。 我们作为开发者，应使用提供的参数执行该工具，并报告 工具执行的结果。

例如，我们知道 LLM 本身并不擅长数学。 如果你的用例涉及偶尔的数学计算，你可能希望向 LLM 提供一个「数学工具」。 通过在发送给 LLM 的请求中声明一个或多个工具， 它可以在认为合适时决定调用其中一个。 给定一个数学问题以及一组数学工具，LLM 可能会决定为了正确回答问题， 它应该首先调用所提供的数学工具之一。

如你所见，当 LLM 可以访问工具时，它可以在合适时决定调用其中一个。

这是一个非常强大的功能。 在这个简单的示例中，我们向 LLM 提供了基础数学工具， 但想象一下，如果我们提供例如 googleSearch 和 sendEmail 工具， 以及类似「我的朋友想知道 AI 领域的近期新闻。将简短摘要发送到 friend@email.com」的查询， 那么它可以使用 googleSearch 工具查找近期新闻， 然后总结并通过 sendEmail 工具发送摘要。

注意

为了提高 LLM 使用正确参数调用正确工具的概率， 我们应提供清晰且无歧义的：

  • 工具名称
  • 工具功能描述及何时应使用
  • 每个工具参数的描述

一条经验法则：如果人类能理解工具的用途及使用方法， LLM 很可能也能理解。

LLM 经过专门微调，能够检测何时调用工具以及如何调用。 有些模型甚至可以同时调用多个工具，例如 OpenAI (opens new window)。

注意

请注意，并非所有模型都支持工具。 要查看哪些模型支持工具，请参阅此页面 (opens new window)上的「Tools」列。

注意

请注意，工具/函数调用与 JSON 模式 (opens new window) 并不相同。

# 两层抽象

LangChain4j 为使用工具提供了两个抽象层次：

  • 低层，使用 ChatModel 和 ToolSpecification API
  • 高层，使用 AI 服务 (opens new window) 和 @Tool 注解的 Java 方法

# 低层工具 API

在低层，你可以使用 ChatModel 的 chat(ChatRequest) 方法。 StreamingChatModel 中也有类似的方法。

创建 ChatRequest 时可以指定一个或多个 ToolSpecification。

ToolSpecification 是包含工具所有信息的对象：

  • 工具的 name（名称）
  • 工具的 description（描述）
  • 工具的 parameters（参数）及其描述
  • 工具的 metadata（元数据）。 默认情况下，它不会发送给 LLM 提供商，你必须在创建 ChatModel 时 显式指定应发送哪些元数据键。 目前，工具元数据仅由 langchain4j-anthropic 模块支持。 当工具由 McpToolProvider (opens new window) 提供时， metadata 可以包含 MCP 特定的条目。

建议尽可能多地提供有关工具的信息： 清晰的名称、全面的描述，以及每个参数的描述等。

如果 LLM 决定调用工具，返回的 AiMessage 将在 toolExecutionRequests 字段中包含数据。 此时，AiMessage.hasToolExecutionRequests() 将返回 true。 取决于 LLM，它可能包含一个或多个 ToolExecutionRequest 对象 （有些 LLM 支持并行调用多个工具）。

每个 ToolExecutionRequest 应包含：

  • 工具调用的 id。请注意，某些 LLM 提供商（例如 Google、Ollama）可能会省略此 ID。
  • 要调用的工具 name，例如：getWeather
  • arguments，例如：{ "city": "London", "temperatureUnit": "CELSIUS" }

你需要使用 ToolExecutionRequest 中的信息手动执行工具。

如果你想将工具执行结果发回 LLM， 需要创建 ToolExecutionResultMessage（每个 ToolExecutionRequest 一个） 并与所有先前的消息一起发送：


String result = "It is expected to rain in London tomorrow.";
ToolExecutionResultMessage toolExecutionResultMessage = ToolExecutionResultMessage.from(toolExecutionRequest, result);
ChatRequest request2 = ChatRequest.builder()
        .messages(List.of(userMessage, aiMessage, toolExecutionResultMessage))
        .toolSpecifications(toolSpecifications)
        .build();
ChatResponse response2 = model.chat(request2);

# 高层工具 API

在高层抽象中，你可以用 @Tool 注解任何 Java 方法， 并在创建 AI 服务 (opens new window) 时指定它们。

AI 服务会自动将此类方法转换为 ToolSpecification， 并在每次与 LLM 交互的请求中包含它们。 当 LLM 决定调用工具时，AI 服务会自动执行相应的方法， 方法的返回值（如有）将被发回 LLM。 你可以在 DefaultToolExecutor 中找到实现细节。

几个工具示例：

@Tool("Searches Google for relevant URLs, given the query")
public List<String> searchGoogle(@P("search query") String query) {
    return googleSearchService.search(query);
}

@Tool("Returns the content of a web page, given the URL")
public String getWebPageContent(@P("URL of the page") String url) {
    Document jsoupDocument = Jsoup.connect(url).get();
    return jsoupDocument.body().text();
}

# 工具方法限制

使用 @Tool 注解的方法：

  • 可以是静态或非静态
  • 可以具有任何可见性（public、private 等）。

# 工具方法参数

使用 @Tool 注解的方法可以接受任意数量的各种类型参数：

  • 基本类型：int、double 等
  • 对象类型：String、Integer、Double 等
  • 自定义 POJO（可包含嵌套 POJO）
  • enum
  • 多态类型（sealed 接口/类，或使用 Jackson @JsonSubTypes / @JsonTypeInfo 注解的类型）——参见多态工具参数
  • List<T>/Set<T>，其中 T 为上述类型之一
  • Map<K,V>（你需要在 @P 的参数描述中手动指定 K 和 V 的类型）

也支持无参数的方法。

# 参数名称

默认情况下，如果未指定 @P 的 name 属性，则通过反射获取参数名称。 然而，没有 -parameters javac 选项时，反射会返回 arg0、arg1 等通用名称。 参数的语义含义会丢失，这可能使 LLM 困惑。

在 @P 中设置 name 在两种情况下很有用：

  1. 缺少 -parameters javac 选项 —— 避免 LLM 看到通用 arg0/arg1 名称。 请注意，Quarkus 和 Spring 等框架默认启用 -parameters， 因此实际的方法参数名称会被保留，使用这些框架时通常无需设置 name。
  2. 为 LLM 自定义名称 —— 当你希望 LLM 看到的参数名称与源代码中的不同时 （例如，以匹配特定 API 契约或提供更描述性的名称）。

示例：

@Tool
void getTemperature(
        @P("Temperature value") double value,
        @P("Unit of temperature") Optional<String> unit) {
    ...
}

# 必填与可选

默认情况下，所有工具方法参数都被视为必填。 这意味着该参数会列在发送给 LLM 的 JSON schema 的 required 数组中， 指示 LLM 必须产生一个值。 可以通过 @P(required = false) 注解使参数变为可选：

@Tool
String getTemperature(String location, @P(required = false) Unit unit) {
    ...
}

注意

required 仅为建议：LLM 仍可能省略参数

required 标志控制发送给 LLM 的 JSON schema（必填参数列在 schema 的 required 数组中）。LLM 应遵守此规则，但实际上它可能 无视 schema 并省略参数。

在 LangChain4j 1.x 中，这仅对基本类型参数（int、long、boolean 等）进行检测—— 缺失的基本类型会触发 ToolArgumentsErrorHandler（参见下方错误处理）。 缺失的对象参数不会被验证：即使 schema 将参数标记为必填，也会向 @Tool 注解的方法传入 null。

我们计划在 LangChain4j 2.0 中消除这种不对称性，使所有必填参数 得到统一验证。如果此计划变更会影响你的用例，请 提交 issue (opens new window)，以便我们在落地前听取你的反馈。

如果你希望有真正的回退而不是 null（或对基本类型参数的错误），请使用 @P(defaultValue = ...)。

# 多态工具参数

工具参数可以是多态类型——其具体子类型由 LLM 在调用时决定。Sealed 接口和 sealed 类无需注解即可工作； 普通抽象类和接口必须使用 Jackson 的 @JsonSubTypes 声明其子类型。 发送给 LLM 的 schema 包含允许子类型的 anyOf，每个子类型带有 鉴别器属性（默认为 "type"），以便 LLM 可以传达它产生了哪种具体 类型；LangChain4j 在调用你的工具方法之前将 LLM 的参数反序列化为正确的子类型。

# @P

方法参数可以选择性地使用 @P 注解。

@P 注解包含以下可选字段：

  • name：LLM 看到的参数名称。如果未指定，则使用实际的方法参数名称。
  • description：参数描述（value 的别名）。默认为空。
  • value：参数描述（description 的别名）。默认为空。
  • required：参数是否必填，默认为 true。

# 参数名称

name 属性覆盖 LLM 将看到的参数名称。 在两种情况下设置 name 很有用：

  1. 缺少 -parameters javac 选项。 没有 -parameters javac 选项时，Java 反射返回 arg0、arg1 等通用名称。 参数的语义含义会丢失，这可能使 LLM 困惑。 设置 name 可以恢复有意义的名称。 请注意，Quarkus 和 Spring 等框架默认启用 -parameters， 因此实际的方法参数名称会被保留，使用这些框架时通常无需设置 name。

  2. 为 LLM 自定义名称。 当你希望 LLM 看到的参数名称与开发者在源代码中使用的名称不同时 （例如，以匹配特定 API 契约或提供更描述性的名称）。

# 并发执行工具

默认情况下，当 LLM 一次调用多个工具时（也称为并行工具调用）， AI 服务会顺序执行它们。如果你希望工具并发执行， 可以在构建 AI 服务时调用 executeToolsConcurrently() 或 executeToolsConcurrently(Executor)。 如果启用其中一个选项，工具将并发执行（有一个例外——见下文）， 使用默认或指定的 Executor。

# 使用 ChatModel 时：

  • 当 LLM 调用多个工具时，它们使用 Executor 在独立线程中并发执行。
  • 当 LLM 调用单个工具时，它在同一（调用者）线程中执行， 不使用 Executor 以避免浪费资源。

# 使用 StreamingChatModel 时：

  • 当 LLM 调用多个工具时，它们使用 Executor 在独立线程中并发执行。 每个工具在调用 StreamingChatResponseHandler.onCompleteToolCall(CompleteToolCall) 后立即执行，无需等待其他工具或响应流式输出完成。
  • 当 LLM 调用单个工具时，它使用 Executor 在独立线程中执行。 我们无法在同一线程中执行，因为在那个时间点， 我们还不知道 LLM 将调用多少个工具。

# 工具搜索

当使用大量工具时， 在每次请求中发送所有工具会显著增加 token 使用量并降低模型性能。 为此，LangChain4j 提供了工具搜索机制， 允许 LLM 自身动态发现工具， 而不是预先暴露所有工具。

核心思想很简单：

  • 最初，LLM 只接触到一种或多种特殊的工具搜索工具
  • LLM 可以调用这些工具来搜索相关工具
  • 找到相关工具后，它们会被包含在后续发送给 LLM 的请求中

这实现了可扩展、token 高效、由模型驱动的工具发现。

# 工具搜索如何工作

工具搜索流程通常如下：

  1. 初始请求：
  • LLM 只看到工具搜索工具（而非完整工具集）
  1. 工具搜索
  • LLM 调用工具搜索工具，描述它需要哪种类型的工具
  • 工具搜索策略将请求与可用工具进行匹配
  1. 工具暴露
  • 匹配的工具被添加到下一次发送给 LLM 的请求中
  1. 工具执行
  • LLM 现在可以正常调用找到的工具

先前找到的工具会在多次工具搜索调用中累积。 每次 LLM 调用工具搜索工具时， 新匹配的工具会被添加到 LLM 可见的现有工具集中（合并，而非替换）。 这意味着 LLM 可见的工具列表会随时间增长。 找到的工具对 LLM 保持可见，直到其对应的 ToolExecutionResultMessage 从 ChatMemory 中被驱逐，且至少直到 AI 服务调用结束。

如果未配置 ChatMemory，找到的工具对 LLM 保持可见 仅直到 AI 服务调用结束。

# 非 Result 的 AI 服务方法返回类型

如果你的 AI 服务方法签名不返回 Result 类型，那么 当有立即工具调用时，你的 chat 方法调用可能成功也可能失败，规则如下：

  • 如果 AI 服务方法返回类型为 void，请求将成功。
  • 如果有任何非立即工具调用，请求将失败并抛出 IllegalConfigurationException 异常。
  • 如果所有工具执行结果均为 null（或 void），且返回类型不是基本类型，请求将成功且返回值为 null。
  • 如果只有一个非 null 工具执行结果，且结果可以解析为返回类型，则请求将成功并返回该工具结果。
  • 如果有多个非 null 工具执行结果，请求将失败并抛出 IllegalConfigurationException 异常。
  • 如果有一个工具执行结果且无法解析为返回类型，请求将失败并抛出 IllegalConfigurationException 异常。

# 单次响应中多个工具调用的立即返回规则

当 LLM 在单次响应中返回多个工具调用时， 循环立即返回（不将结果发回 LLM）仅当同时满足以下两个条件：

  1. 没有工具出错。 任何工具调用中的错误都会强制重新处理，以便 LLM 在下一轮对错误做出反应。
  2. 要么响应中的每个工具都是 IMMEDIATE（没有混合 TO_LLM 工具）要么最后一个工具是 IMMEDIATE_IF_LAST（见下一节）。

示例（工具按 LLM 在单次响应中返回的顺序列出； (err) 标记执行出错的工具）：

响应中的工具调用 结果 原因
[IMMEDIATE] 立即返回 唯一工具是 IMMEDIATE
[IMMEDIATE, IMMEDIATE] 立即返回 每个工具都是 IMMEDIATE/IMMEDIATE_IF_LAST
[IMMEDIATE, TO_LLM] 重新处理 TO_LLM 使全立即规则失效
[IMMEDIATE_IF_LAST] 立即返回 最后一个工具是 IMMEDIATE_IF_LAST
[TO_LLM, IMMEDIATE_IF_LAST] 立即返回 最后一个工具是 IMMEDIATE_IF_LAST
[IMMEDIATE_IF_LAST, TO_LLM] 重新处理 不是最后一个，且 TO_LLM 使全立即规则失效
[IMMEDIATE, IMMEDIATE_IF_LAST] 立即返回 最后一个工具是 IMMEDIATE_IF_LAST
[IMMEDIATE_IF_LAST, IMMEDIATE] 立即返回 每个工具都是 IMMEDIATE/IMMEDIATE_IF_LAST
[TO_LLM, IMMEDIATE_IF_LAST, IMMEDIATE] 重新处理 不是最后一个，且 TO_LLM 使全立即规则失效
[IMMEDIATE_IF_LAST(err)] 重新处理 任何错误都会禁用立即返回
[TO_LLM(err), IMMEDIATE_IF_LAST] 重新处理 任何错误都会禁用立即返回

有关完整的立即返回与重新处理矩阵，请参阅 ReturnBehavior 的 Javadoc。

# 用于显式结束操作序列的 IMMEDIATE_IF_LAST

ReturnBehavior.IMMEDIATE_IF_LAST 适用于 LLM 用于显式信号 多步操作结束的工具——例如，LLM 在一系列点击、导航等之后附加的 endExecutionAndGetFinalResult 工具。

没有 IMMEDIATE_IF_LAST 时，LLM 通常需要两轮来结束执行： 一轮混合工作工具（TO_LLM）与结束工具， 以及第二轮 LLM 在看到所有结果后 单独调用结束工具。循环仅在第二轮立即返回。

使用 IMMEDIATE_IF_LAST 时，一旦 LLM 将该工具放在 响应的最后，循环立即返回——每次调用节省一轮完整的 LLM 往返。

class ScreenAutomation {

    @Tool
    String leftMouseClick(int x, int y) { /* ... */ }

    @Tool
    String typeText(String text) { /* ... */ }

    @Tool(returnBehavior = ReturnBehavior.IMMEDIATE_IF_LAST)
    String endExecutionAndGetFinalResult(String summary) { return summary; }
}

# 处理工具执行错误

默认情况下，当使用 @Tool 注解的方法抛出 Exception 时， Exception 的消息（e.getMessage()）将作为工具执行的结果发送给 LLM。 这允许 LLM 纠正其错误并在认为必要时重试。

注意

推荐：生产环境中不要将原始异常消息发送给 LLM

当前默认行为将原始异常消息发回 LLM。在生产环境中这可能泄露 内部应用数据：堆栈跟踪、文件路径、嵌入在错误字符串中的凭据、 下游 API 响应、错误消息中的 PII 等。 一旦输入 LLM，此内容可能流入响应、聊天历史、可观测性管道、 以及 LLM 提供商的日志。

配置 ToolExecutionErrorHandler 返回通用消息或经过整理/净化的 失败描述，并依赖日志和可观测性事件获取底层详情。

我们计划在 LangChain4j 2.0 中将默认行为更改为「抛出异常并中止 AI 服务调用」。 如果此计划变更会影响你的用例，请 提交 issue (opens new window)，以便我们在落地前听取你的反馈。

你可以通过在 AI 服务上配置 ToolExecutionErrorHandler 来自定义此行为：

Assistant assistant = AiServices.builder(Assistant.class)
        .chatModel(chatModel)
        .tools(tools)
        .toolExecutionErrorHandler((error, errorContext) -> ToolErrorHandlerResult.text("Tool execution failed."))
        .build();

# 补偿工具操作

当 AI 服务使用多个工具完成任务时，一个工具的失败 可能使系统处于不一致状态——某些工具已成功执行 而其他工具尚未执行。例如，在银行转账中，LLM 可能 先向收款人账户入账，然后由于余额不足 无法从付款人账户扣款，导致收款人获得额外资金。

为此，你可以启用工具错误时的补偿。启用后， 如果任何工具执行失败，所有先前成功且声明了 补偿操作的工具调用会自动按相反顺序撤销。

# 使用 @CompensateFor 声明补偿操作

在方法上使用 @CompensateFor 注解将其声明为 @Tool 的补偿操作。value 必须与暴露给 LLM 的工具名称匹配—— 设置了 @Tool(name = ...) 时使用该属性，否则使用 @Tool 方法名称（默认作为工具名称）。 补偿方法必须与工具有相同的参数类型， 或接受单个 ToolExecution 参数。

选项 1：相同参数类型 —— 补偿方法接收 传递给原始工具的相同参数：

class BankAccountService {

    @Tool("credits money to a bank account")
    void credit(String name, double amount) {
        accounts.merge(name, amount, Double::sum);
    }

    @CompensateFor("credit")
    void uncredit(String name, double amount) {
        accounts.merge(name, -amount, Double::sum);
    }

    @Tool("withdraws money from a bank account")
    void withdraw(String name, double amount) {
        if (accounts.getOrDefault(name, 0.0) < amount) {
            throw new RuntimeException("Insufficient funds");
        }
        accounts.merge(name, -amount, Double::sum);
    }

    @CompensateFor("withdraw")
    void unwithdraw(String name, double amount) {
        accounts.merge(name, amount, Double::sum);
    }
}

选项 2：ToolExecution 参数 —— 补偿方法接收完整的 ToolExecution，可以访问原始参数和工具的 返回值。这在撤销操作需要原始执行 产生的信息（例如交易 ID）时很有用：

class BankAccountService {

        accounts.merge(name, amount, Double::sum);
        return createTransactionRecord(name, amount); // e.g. "TX-42"
    }

    @CompensateFor("credit")
    void uncredit(ToolExecution toolExecution) {
        String transactionId = toolExecution.result(); // "TX-42"
        reverseTransaction(transactionId);
    }
}

# 启用补偿

构建 AI 服务时调用 .compensateOnToolErrors(true)：

Assistant assistant = AiServices.builder(Assistant.class)
        .chatModel(model)
        .tools(new BankAccountService())
        .compensateOnToolErrors(true)
        .build();

使用此配置，如果 LLM 调用 credit("Dmytro", 100) 然后 withdraw("Mario", 100) 失败，框架将自动调用 uncredit("Dmytro", 100) 撤销入账。框架不会抛出异常， 而是为每个工具向 LLM 发送信息性结果消息： 已回滚的工具收到类似 "Tool 'credit' was executed successfully but was rolled back due to failure of tool 'withdraw'" 的消息， 失败的工具收到其正常错误消息。这保持 ChatMemory 一致，让 LLM 决定下一步——重试、通知用户或采取不同方法。

没有 .compensateOnToolErrors(true) 时，错误会照常发回 LLM，不会发生 补偿——即使存在 @CompensateFor 注解。

# 验证

启用 .compensateOnToolErrors(true) 时，每个 @CompensateFor 都会被验证：

  • 引用的工具必须存在于同一对象上（按名称）。
  • 补偿方法必须与工具有完全相同的参数类型， 或接受单个 ToolExecution 参数。

如果任一检查失败，会立即抛出 IllegalConfigurationException， 因此配置错误在启动时而非运行时被捕获。 如果未启用 .compensateOnToolErrors(true)，@CompensateFor 注解 会被静默忽略且不执行验证。

# 说明与限制

注意

补偿是尽力而为：如果补偿操作本身抛出异常，会以 WARN 级别 记录日志，其余补偿操作继续执行。

注意

@CompensateFor 方法不会暴露给 LLM——它们是内部补偿 基础设施，不会出现在工具规范中。

注意

补偿操作始终按相反顺序顺序执行，即使工具 执行通过 .executeToolsConcurrently() 配置为并行运行。

注意

@CompensateFor 方法可以从超类继承，与 @Tool 方法的发现方式一致。

注意

@CompensateFor 仅适用于 @Tool 注解的方法。以编程或 动态定义的工具（例如 MCP 工具、通过 ToolSpecification 注册的工具） 不受支持。

注意

补偿工具操作目前标记为实验性，未来版本可能会演进。
