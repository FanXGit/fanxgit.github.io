# RAG（检索增强生成）

LLM 的知识仅限于其训练所用的数据。若希望让 LLM 了解领域知识或专有数据，你可以：

  • 使用 RAG，本节将介绍这一方法
  • 用你的数据对 LLM 进行微调
  • 结合 RAG 与微调 (opens new window)

# 什么是 RAG？

简而言之，RAG 是从你的数据中查找相关信息，并在发送给 LLM 之前将其注入提示词的方式。这样 LLM 有望获得相关信息，并基于这些信息作答，从而降低产生幻觉的概率。

相关信息可通过多种信息检索 (opens new window)方法查找。最常用的是：

  • 全文（关键词）搜索。该方法使用 TF-IDF、BM25 等技术，通过将查询中的关键词（例如用户所问内容）与文档库匹配来搜索文档。它根据这些关键词在各文档中的频率与相关性对结果排序。
  • 向量搜索，也称「语义搜索」。文本文档通过嵌入模型转换为数值向量。随后基于查询向量与文档向量之间的余弦相似度或其他相似度/距离度量来查找并排序文档，从而捕捉更深层的语义含义。
  • 混合搜索。结合多种搜索方法（例如全文 + 向量）通常能提升搜索效果。

目前，本页主要聚焦向量搜索。全文与混合搜索目前仅由 Azure AI Search 集成和 Elasticsearch 支持，详见 AzureAiSearchContentRetriever 和 ElasticsearchContentRetriever。我们计划在不久的将来扩展 RAG 工具箱，纳入全文与混合搜索。

# RAG 阶段

RAG 过程分为索引（indexing）与检索（retrieval）两个阶段。LangChain4j 为两个阶段都提供了工具。

# 索引

在索引阶段，文档会经过预处理，以便在检索阶段高效搜索。

该过程因所用的信息检索方法而异。对于向量搜索，通常包括：清理文档、用附加数据与元数据丰富文档、将其拆分为更小的片段（即分块/chunking）、对这些片段进行嵌入，最后存入嵌入存储（即向量数据库）。

索引阶段通常在离线进行，意味着无需让终端用户等待其完成。例如，可通过 cron 任务在周末每周重新索引一次公司内部文档。负责索引的代码也可以是仅处理索引任务的独立应用。

但在某些场景下，终端用户可能希望上传自定义文档以供 LLM 使用。此时索引应在线进行，并作为主应用的一部分。

# 检索

检索阶段通常在线进行，当用户提交应利用已索引文档回答的问题时触发。

该过程因所用的信息检索方法而异。对于向量搜索，通常包括：对用户查询（问题）进行嵌入，并在嵌入存储中执行相似度搜索。随后将相关片段（原始文档的片段）注入提示词并发送给 LLM。

# LangChain4j 中的 RAG 形态

LangChain4j 提供三种 RAG 形态：

  • Easy RAG (opens new window)：入门 RAG 最简单的方式
  • Naive RAG (opens new window)：使用向量搜索的基础 RAG 实现
  • Advanced RAG (opens new window)：模块化 RAG 框架，支持查询变换、从多源检索、重排序等额外步骤

# Easy RAG

LangChain4j 提供「Easy RAG」功能，尽可能简化 RAG 入门。你无需了解嵌入、选择向量存储、挑选合适的嵌入模型、研究如何解析与拆分文档等。只需指向你的文档，LangChain4j 会完成其余工作。

若需要可定制的 RAG，请跳至下一节 (opens new window)。

若使用 Quarkus，还有更简单的 Easy RAG 方式。请参阅 Quarkus 文档 (opens new window)。

注意

这种「Easy RAG」的质量当然会低于量身定制的 RAG 配置。然而，这是开始学习 RAG 和/或做概念验证的最简单方式。之后，你可以从 Easy RAG 平滑过渡到更高级的 RAG，逐步调整与定制更多方面。

# 核心 RAG API

LangChain4j 提供丰富的 API，便于构建从简单到高级的自定义 RAG 流水线。本节介绍主要领域类与 API。

# Document

Document 类表示完整文档，例如单个 PDF 文件或网页。目前 Document 只能表示文本信息，未来更新将支持图像与表格。

实用方法
  • Document.text() 返回 Document 的文本
  • Document.metadata() 返回 Document 的 Metadata（见下文「Metadata」一节）
  • Document.toTextSegment() 将 Document 转换为 TextSegment（见下文「TextSegment」一节）
  • Document.from(String, Metadata) 从文本与 Metadata 创建 Document
  • Document.from(String) 从文本创建 Document，Metadata 为空

# Metadata

每个 Document 包含 Metadata。它存储关于 Document 的元信息，例如名称、来源、最后更新日期、所有者或任何其他相关细节。

Metadata 以键值映射形式存储，键为 String 类型，值可为以下类型之一：String、Integer、Long、Float、Double、UUID。

Metadata 在多个方面很有用：

  • 将 Document 内容纳入 LLM 提示词时，也可一并纳入 metadata 条目，为 LLM 提供额外参考信息。例如，提供 Document 名称与来源有助于 LLM 更好理解内容。
  • 搜索要纳入提示词的相关内容时，可按 Metadata 条目过滤。例如，可将语义搜索限定为属于特定所有者的 Document。
  • 当 Document 来源更新时（例如文档的某一页），可通过 metadata 条目（例如 "id"、"source" 等）轻松定位对应 Document，并在 EmbeddingStore 中同步更新。
实用方法
  • Metadata.from(Map) 从 Map 创建 Metadata
  • Metadata.put(String key, String value) / put(String, int) 等，向 Metadata 添加条目
  • Metadata.putAll(Map) 向 Metadata 添加多个条目
  • Metadata.getString(String key) / getInteger(String key) 等，返回 Metadata 条目的值，并转换为所需类型
  • Metadata.containsKey(String key) 检查 Metadata 是否包含指定键的条目
  • Metadata.remove(String key) 按键从 Metadata 移除条目
  • Metadata.copy() 返回 Metadata 的副本
  • Metadata.toMap() 将 Metadata 转换为 Map
  • Metadata.merge(Metadata) 将当前 Metadata 与另一 Metadata 合并

# Document Loader

你可以从 String 创建 Document，但更简单的方法是使用库中包含的文档加载器之一：

  • langchain4j 模块中的 FileSystemDocumentLoader
  • langchain4j 模块中的 ClassPathDocumentLoader
  • langchain4j 模块中的 UrlDocumentLoader
  • langchain4j-document-loader-amazon-s3 模块中的 AmazonS3DocumentLoader
  • langchain4j-document-loader-azure-storage-blob 模块中的 AzureBlobStorageDocumentLoader
  • langchain4j-document-loader-github 模块中的 GitHubDocumentLoader
  • langchain4j-document-loader-google-cloud-storage 模块中的 GoogleCloudStorageDocumentLoader
  • langchain4j-document-loader-selenium 模块中的 SeleniumDocumentLoader
  • langchain4j-document-loader-playwright 模块中的 PlaywrightDocumentLoader
  • langchain4j-document-loader-tencent-cos 模块中的 TencentCosDocumentLoader

# Document Parser

Document 可表示 PDF、DOC、TXT 等多种格式的文件。为解析这些格式，提供了 DocumentParser 接口及库中的多种实现：

  • langchain4j 模块中的 TextDocumentParser，可解析纯文本格式（如 TXT、HTML、MD 等）
  • langchain4j-document-parser-apache-pdfbox 模块中的 ApachePdfBoxDocumentParser，可解析 PDF
  • langchain4j-document-parser-apache-poi 模块中的 ApachePoiDocumentParser，可解析 MS Office 格式（如 DOC、DOCX、PPT、PPTX、XLS、XLSX 等）
  • langchain4j-document-parser-apache-tika 模块中的 ApacheTikaDocumentParser，可自动检测并解析几乎所有现有文件格式
  • langchain4j-document-parser-docling 模块中的 DoclingDocumentParser，使用 Docling Java (opens new window) 与 Docling (opens new window) 处理文档
  • langchain4j-document-parser-markdown 模块中的 MarkdownDocumentParser，可解析 Markdown 格式
  • langchain4j-document-parser-yaml 模块中的 YamlDocumentParser，可解析 YAML 格式

以下示例展示如何从文件系统加载一个或多个 Document：

// Load a single document
Document document = FileSystemDocumentLoader.loadDocument("/home/langchain4j/file.txt", new TextDocumentParser());

// Load all documents from a directory
List<Document> documents = FileSystemDocumentLoader.loadDocuments("/home/langchain4j", new TextDocumentParser());

// Load all *.txt documents from a directory
PathMatcher pathMatcher = FileSystems.getDefault().getPathMatcher("glob:*.txt");
List<Document> documents = FileSystemDocumentLoader.loadDocuments("/home/langchain4j", pathMatcher, new TextDocumentParser());

// Load all documents from a directory and its subdirectories
List<Document> documents = FileSystemDocumentLoader.loadDocumentsRecursively("/home/langchain4j", new TextDocumentParser());

# Document Transformer

DocumentTransformer 实现可执行多种文档变换，例如：

  • 清理：移除 Document 文本中不必要的噪声，节省 token 并减少干扰
  • 过滤：完全排除特定 Document，使其不参与搜索
  • 丰富：向 Document 添加附加信息，可能提升搜索结果
  • 摘要：对 Document 生成摘要并存入 Metadata，以便后续纳入每个 TextSegment（见下文），可能改善搜索
  • 等等

在此阶段也可添加、修改或移除 Metadata 条目。

目前开箱即用的唯一实现是 langchain4j-document-transformer-jsoup 模块中的 HtmlToTextDocumentTransformer，可从原始 HTML 提取所需文本内容与 metadata 条目。

由于没有放之四海而皆准的方案，我们建议实现针对你独特数据的自定义 DocumentTransformer。

# Graph Transformer

GraphTransformer 是将非结构化 Document 对象转换为结构化 GraphDocument 的接口，通过提取语义图元素（如节点与关系）实现。它适合将原始文本转换为结构化语义图。

GraphTransformer 将原始文档转换为 GraphDocument，其中包含：

  • 表示文本中实体或概念的节点（GraphNode）集合
  • 表示这些实体如何连接的关系（GraphEdge）集合
  • 作为 source 的原始 Document

默认实现是 LLMGraphTransformer，使用语言模型（如 OpenAI）通过提示工程从自然语言中提取图信息。

# 主要优势

  • 实体与关系提取：识别关键概念及其语义连接
  • 图表示：输出可直接集成到知识图或图数据库
  • 模型驱动解析：使用大语言模型从非结构化文本推断结构

# 使用示例

import dev.langchain4j.data.document.Document;
import dev.langchain4j.model.openai.OpenAiChatModel;
import dev.langchain4j.community.data.document.graph.GraphDocument;
import dev.langchain4j.community.data.document.graph.GraphNode;
import dev.langchain4j.community.data.document.graph.GraphEdge;
import dev.langchain4j.community.data.document.transformer.graph.GraphTransformer;
import dev.langchain4j.community.data.document.transformer.graph.llm.LLMGraphTransformer;

import java.time.Duration;
import java.util.Set;

public class GraphTransformerExample {
    public static void main(String[] args) {
        // Create a GraphTransformer backed by an LLM
        GraphTransformer transformer = new LLMGraphTransformer(
            OpenAiChatModel.builder()
                .apiKey(System.getenv("OPENAI_API_KEY"))
                .timeout(Duration.ofSeconds(60))
                .build()
        );

        // Input document
        Document document = Document.from("Barack Obama was born in Hawaii and served as the 44th President of the United States.");

        // Transform the document
        GraphDocument graphDocument = transformer.transform(document);

        // Access nodes and relationships
        Set<GraphNode> nodes = graphDocument.nodes();
        Set<GraphEdge> relationships = graphDocument.relationships();

        nodes.forEach(System.out::println);
        relationships.forEach(System.out::println);
    }
}

# Text Segment

文档加载完成后，需要将其拆分（分块）为更小的片段（pieces）。LangChain4j 的领域模型包含 TextSegment 类，表示 Document 的一个片段。顾名思义，TextSegment 只能表示文本信息。

分还是不分？

将完整知识库而非少量相关片段纳入提示词，可能有以下原因：

  • LLM 上下文窗口有限，完整知识库可能无法全部放入
  • 提示词中信息越多，LLM 处理并响应所需时间越长
  • 提示词中信息越多，费用越高
  • 提示词中的无关信息可能干扰 LLM，增加幻觉概率
  • 提示词中信息越多，越难解释 LLM 是基于哪些信息作答

通过将知识库拆分为更小、更易消化的片段，可缓解上述问题。片段应多大？这是个好问题。一如既往，视情况而定。

目前有两种广泛使用的做法：

  1. 每个文档（如 PDF、网页等）是原子且不可分割的。在 RAG 流水线检索时，检索 N 个最相关文档并注入提示词。由于文档可能很长，此情况下很可能需要使用长上下文 LLM。当你需要检索完整文档时（例如不能遗漏细节），此方式适用。
  • 优点：不丢失上下文
  • 缺点：
  • 消耗更多 token
  • 有时文档包含多个章节/主题，并非都与查询相关
  • 向量搜索质量下降，因为不同大小的完整文档被压缩为单一固定长度向量
  1. 文档拆分为更小片段，如章节、段落，有时甚至是句子。在 RAG 流水线检索时，检索 N 个最相关片段并注入提示词。挑战在于确保每个片段为 LLM 提供足够上下文/信息以便理解。缺失上下文可能导致 LLM 误解给定片段并产生幻觉。常见策略是重叠拆分文档，但这并不能完全解决问题。多种高级技术可在此提供帮助，例如「句子窗口检索」「自动合并检索」「父文档检索」。此处不展开细节，但本质上这些方法有助于在检索片段周围获取更多上下文，在检索片段前后为 LLM 提供附加信息。
  • 优点：
  • 向量搜索质量更好
  • 减少 token 消耗
  • 缺点：仍可能丢失部分上下文
实用方法
  • TextSegment.text() 返回 TextSegment 的文本
  • TextSegment.metadata() 返回 TextSegment 的 Metadata
  • TextSegment.from(String, Metadata) 从文本与 Metadata 创建 TextSegment
  • TextSegment.from(String) 从文本创建 TextSegment，Metadata 为空

# Document Splitter

LangChain4j 提供 DocumentSplitter 接口及多种开箱即用实现：

  • DocumentByParagraphSplitter
  • DocumentByLineSplitter
  • DocumentBySentenceSplitter
  • DocumentByWordSplitter
  • DocumentByCharacterSplitter
  • DocumentByRegexSplitter
  • 递归：DocumentSplitters.recursive(...)

它们的工作方式如下：

  1. 实例化 DocumentSplitter，指定所需的 TextSegment 大小，以及可选的字符或 token 重叠量
  2. 调用 DocumentSplitter 的 split(Document) 或 splitAll(List) 方法
  3. DocumentSplitter 将给定 Document 拆分为更小单元，具体因拆分器而异。例如，DocumentByParagraphSplitter 按段落（由两个及以上连续换行符定义）拆分；DocumentBySentenceSplitter 使用 OpenNLP 库的句子检测器拆分为句子，以此类推
  4. DocumentSplitter 再将这些更小单元（段落、句子、词等）组合为 TextSegment，尽量在每个 TextSegment 中纳入更多单元，同时不超过步骤 1 设定的上限。若仍有单元过大无法放入 TextSegment，则调用子拆分器——另一个能将过大单元拆分为更细粒度单元的 DocumentSplitter。所有 Metadata 条目从 Document 复制到每个 TextSegment。为每个文本片段添加唯一 metadata 条目 "index"：第一个 TextSegment 为 index=0，第二个为 index=1，依此类推

# Text Segment Transformer

TextSegmentTransformer 与上文 DocumentTransformer 类似，但变换的是 TextSegment。

与 DocumentTransformer 一样，没有通用方案，我们建议实现针对你独特数据的自定义 TextSegmentTransformer。

一种对提升检索效果较有效的做法是在每个 TextSegment 中包含 Document 标题或简短摘要。

# Embedding Store

EmbeddingStore 接口表示 Embedding 的存储，即向量数据库。它支持存储并高效搜索相似（在嵌入空间中接近）的 Embedding。

当前支持的嵌入存储见此处 (opens new window)。

EmbeddingStore 可单独存储 Embedding，或与对应 TextSegment 一并存储：

  • 可仅按 ID 存储 Embedding。原始嵌入数据可存于别处，通过 ID 关联
  • 可同时存储 Embedding 与原始被嵌入数据（通常是 TextSegment）
实用方法
  • EmbeddingStore.add(Embedding) 将给定 Embedding 加入存储并返回随机 ID
  • EmbeddingStore.add(String id, Embedding) 将给定 Embedding 以指定 ID 加入存储
  • EmbeddingStore.add(Embedding, TextSegment) 将给定 Embedding 与关联 TextSegment 加入存储并返回随机 ID
  • EmbeddingStore.addAll(List) 将给定 Embedding 列表加入存储并返回随机 ID 列表
  • EmbeddingStore.addAll(List, List) 将给定 Embedding 列表与关联 TextSegment 列表加入存储并返回随机 ID 列表
  • EmbeddingStore.addAll(List ids, List, List) 将给定 Embedding 列表与关联 ID、TextSegment 列表加入存储
  • EmbeddingStore.search(EmbeddingSearchRequest) 搜索最相似的 Embedding
  • EmbeddingStore.remove(String id) 按 ID 从存储移除单个 Embedding
  • EmbeddingStore.removeAll(Collection ids) 从存储移除 ID 在给定集合中的所有 Embedding
  • EmbeddingStore.removeAll(Filter) 从存储移除匹配指定 Filter 的所有 Embedding
  • EmbeddingStore.removeAll() 从存储移除所有 Embedding

# EmbeddingSearchRequest

EmbeddingSearchRequest 表示在 EmbeddingStore 中搜索的请求，包含以下属性：

  • Embedding queryEmbedding：用作参考的嵌入
  • int maxResults：返回的最大结果数。可选参数。默认：3
  • double minScore：最低分数，范围 0 到 1（含）。仅返回 score >= minScore 的嵌入。可选参数。默认：0
  • Filter filter：搜索时对 Metadata 应用的过滤器。仅返回 Metadata 匹配 Filter 的 TextSegment

Filter 允许在执行向量搜索时按 Metadata 条目过滤。

  • IsGreaterThan
  • IsGreaterThanOrEqualTo
  • IsLessThan
  • IsLessThanOrEqualTo
  • IsIn
  • IsNotIn
  • ContainsString
  • And
  • Not
  • Or

# Advanced RAG

LangChain4j 可通过以下核心组件实现 Advanced RAG：

  • QueryTransformer
  • QueryRouter
  • ContentRetriever
  • ContentAggregator
  • ContentInjector

以下示意图展示这些组件如何协同工作：

流程如下：

  1. 用户产生 UserMessage，转换为 Query
  2. QueryTransformer 将 Query 转换为一个或多个 Query
  3. QueryRouter 将每个 Query 路由到一个或多个 ContentRetriever
  4. 每个 ContentRetriever 为每个 Query 检索相关 Content
  5. ContentAggregator 将所有检索到的 Content 合并为单一最终排序列表
  6. 该 Content 列表注入原始 UserMessage
  7. 最后，包含原始查询与注入相关内容的 UserMessage 发送给 LLM

请参阅各组件的 Javadoc 以了解更多细节。

# Query Transformer

QueryTransformer 将给定的 Query 转换为一个或多个 Query。目标是通过修改或扩展原始 Query 提升检索质量。

改善检索的已知方法包括：

  • 查询压缩
  • 查询扩展
  • 查询重写
  • Step-back prompting
  • 假设文档嵌入（HyDE）

更多细节见此处 (opens new window)。

LangChain4j 还有可选的社区 Prompt Repetition (opens new window) 模块，提供 RepeatingQueryTransformer。它在内容检索前重复检索查询，应用于变换查询本身，而非发送给模型的最终增强提示词。

# Default Query Transformer

DefaultQueryTransformer 是 DefaultRetrievalAugmentor 中使用的默认实现。它不对 Query 做任何修改，仅原样传递。

# Compressing Query Transformer

CompressingQueryTransformer 使用 LLM 将给定的 Query 与先前对话压缩为独立 Query。当用户可能提出指向前序问题或回答中信息的追问时很有用。

示例：

User: Tell me about John Doe
AI: John Doe was a ...
User: Where did he live?

3

单独看查询 Where did he live? 无法检索所需信息，因为没有明确提到 John Doe，不清楚 he 指谁。

使用 CompressingQueryTransformer 时，LLM 会阅读整个对话，将 Where did he live? 转换为 Where did John Doe live?。

# Expanding Query Transformer

ExpandingQueryTransformer 使用 LLM 将给定的 Query 扩展为多个 Query。这很有用，因为 LLM 可以用多种方式改写 Query，有助于检索更多相关内容。

# Content

Content 表示与用户 Query 相关的内容。目前限于文本内容（即 TextSegment），未来可能支持其他模态（如图像、音频、视频等）。

# Content Retriever

ContentRetriever 使用给定 Query 从底层数据源检索 Content。底层数据源几乎可以是任何内容：

  • 嵌入存储
  • 全文搜索引擎
  • 向量与全文混合搜索
  • 网页搜索引擎
  • 知识图
  • SQL 数据库
  • 等等

ContentRetriever 返回的 Content 列表按相关性从高到低排序。

当只有一个 Query 和一个 ContentRetriever 时，DefaultRetrievalAugmentor 在同一线程中执行查询路由与内容检索。否则，使用 Executor 并行处理。默认使用修改版（keepAliveTime 为 1 秒而非 60 秒）的 Executors.newCachedThreadPool()，但创建 DefaultRetrievalAugmentor 时可提供自定义 Executor 实例：

DefaultRetrievalAugmentor.builder()
        ...
        .executor(executor)
        .build;

# 控制聊天记忆中存储的内容

将 RetrievalAugmentor 与 AI 服务 (opens new window) 一起使用时，可控制聊天记忆中存储的是增强后的用户消息（已注入检索到的 Content）还是原始用户消息。

该行为通过 AiServices 构建器上的 storeRetrievedContentInChatMemory 选项配置。

# 配置

  • true（默认） 在聊天记忆中存储增强后的 UserMessage（原始查询加检索内容）。 发送给 LLM 的也是同一条增强消息。

  • false 在聊天记忆中仅存储原始 UserMessage（不含检索内容）。 推理期间仍向 LLM 发送增强消息。

仅存储原始用户消息在希望保持聊天历史简洁、与用户实际输入一致，同时仍为 LLM 提供检索上下文以生成答案时很有用。

# 示例

interface Assistant {

    String chat(String userMessage);
}

ChatModel chatModel = OpenAiChatModel.builder()
    .apiKey(System.getenv("OPENAI_API_KEY"))
    .modelName(GPT_4_O_MINI)
    .build();

MessageWindowChatMemory chatMemory =
    MessageWindowChatMemory.withMaxMessages(10);

RetrievalAugmentor retrievalAugmentor =
    DefaultRetrievalAugmentor.builder()
        .contentRetriever(
            EmbeddingStoreContentRetriever.from(embeddingStore, embeddingModel))
        .build();

Assistant assistant = AiServices.builder(Assistant.class)
    .chatModel(chatModel)
    .chatMemory(chatMemory)
    .retrievalAugmentor(retrievalAugmentor)
    // Store only the original user message in chat memory
    .storeRetrievedContentInChatMemory(false)
    .build();
