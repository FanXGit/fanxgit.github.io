# 1. 存储引擎

# 1.1 InnoDB 整体架构

# 概念定义

InnoDB 是 MySQL 5.5 起默认的事务型存储引擎，支持 ACID、行级锁、外键、崩溃恢复。整体分为内存结构与磁盘结构两层。

# 底层原理

┌─────────────────────────────────────────────────────────┐
│                    内存层 (Memory)                       │
│  Buffer Pool │ Change Buffer │ Log Buffer │ AHI 等      │
└─────────────────────────────────────────────────────────┘
                          ↕ 刷盘 / 读取
┌─────────────────────────────────────────────────────────┐
│                    磁盘层 (Disk)                         │
│  表空间(.ibd) │ redo log │ undo log │ 系统表空间         │
└─────────────────────────────────────────────────────────┘

组件 作用
Buffer Pool 缓存数据页、索引页，减少磁盘 IO
Change Buffer 缓存二级索引页的写操作（INSERT/UPDATE/DELETE），后台 merge
Log Buffer 缓存 redo log，批量刷盘
Adaptive Hash Index (AHI) 热点页自动建哈希索引，加速等值查询
Doublewrite Buffer 防 partial page write，先写共享表空间再写数据文件

后台线程：Master Thread（刷脏页/合并 Change Buffer）、IO Thread、Purge Thread（清理 undo）、Page Cleaner Thread。

# 高频面试考点

  • InnoDB 与 MyISAM 核心区别：InnoDB 有事务/行锁/聚簇索引/崩溃恢复；MyISAM 无事务、表锁、非聚簇索引。
  • 为什么 InnoDB 必须有主键：数据按主键组织成 B+ 树，无主键会选唯一非空列或隐式 6 字节 ROW_ID。
  • Change Buffer 只对二级索引生效，聚簇索引变更直接写 Buffer Pool。

# 开发易错坑点

  • 误以为 ENGINE=InnoDB 就自动有事务——需在 Spring @Transactional 或手动 BEGIN/COMMIT 才生效。
  • 把 SHOW ENGINE INNODB STATUS 当日常监控——输出冗长，生产用 Performance Schema / Prometheus exporter。

# 1.2 页（Page）结构

# 概念定义

InnoDB 磁盘 IO 的最小逻辑单位是 16KB 页（innodb_page_size，默认 16384）。表数据、索引、undo 都以页形式存储。

# 底层原理

数据页（Index Page / Leaf Page）结构：

┌──────────────────────────────────────┐
│ File Header (38B)  页号、表空间、校验和 │
├──────────────────────────────────────┤
│ Page Header (56B)  槽数量、方向链表    │
├──────────────────────────────────────┤
│ Infimum + Supremum  虚拟最小/最大记录   │
├──────────────────────────────────────┤
│ User Records         实际行数据（槽指针）│
├──────────────────────────────────────┤
│ Free Space           未使用空间         │
├──────────────────────────────────────┤
│ Page Directory       稀疏槽，二分查找    │
├──────────────────────────────────────┤
│ File Trailer (8B)    校验和             │
└──────────────────────────────────────┘

# 高频面试考点

  • 为什么 B+ 树节点大小设为 16KB：匹配磁盘块大小，一次 IO 读一整页，树高低（千万级数据约 3~4 层）。
  • 页分裂是 insert 慢的原因之一，顺序自增主键比 UUID 随机主键插入友好。

# 开发易错坑点

  • UUID 做主键导致频繁页分裂、索引碎片，写入性能差。
  • VARCHAR(65535) 等大字段放主表——应拆表或只存 URL，Dynamic 格式虽溢出但仍影响页内记录数。

# 2.1 聚簇索引 vs 二级索引

# 概念定义

     [10|30|50]                        [name 索引]
    /    |    \                      /           \
  行数据  行数据  行数据          (name, pk)   (name, pk)
                                  ↓ 回表
                              聚簇索引查完整行

# 2.2 联合索引与最左匹配

# 概念定义

联合索引是多列组成的 B+ 树，按列顺序排序；最左前缀原则指查询从索引最左列开始连续匹配才有效。

# 底层原理

索引 (age, name, city) 排序规则：先按 age，age 相同按 name，再按 city。

(18, Alice, BJ) → (18, Bob, SH) → (25, Tom, GZ)
1
  • WHERE age = 18 AND name = 'Alice' ✅ 用到 age + name
  • WHERE name = 'Alice' ❌ 跳过 age，无法用该索引（全表或别的索引）
  • WHERE age = 18 AND city = 'BJ' ✅ 只用到 age（name 未出现在条件，city 无法跳过 name 使用）

# 示例 SQL

-- 验证最左匹配
EXPLAIN SELECT * FROM user WHERE age = 25;                    -- key: idx_age_name
EXPLAIN SELECT * FROM user WHERE name = 'Tom';                -- key: NULL 或 idx_name
EXPLAIN SELECT * FROM user WHERE age = 25 AND name = 'Tom';   -- key: idx_age_name, key_len 更长

-- 查看 key_len 判断用了几列（需结合字段类型计算）
EXPLAIN SELECT * FROM user WHERE age = 25 AND name = 'Tom' AND city = 'GZ';

# 2.6 索引设计规范

# 概念定义

面向 OLTP 的 InnoDB 索引设计原则，平衡读写、空间与维护成本。

# 底层原理

  1. 主键：短、自增、无业务含义

# 3.1 四大隔离级别

# 概念定义

级别 脏读 不可重复读 幻读
READ UNCOMMITTED 可能 可能 可能
READ COMMITTED 否 可能 可能
REPEATABLE READ（InnoDB 默认） 否 否 理论上可能，InnoDB MVCC+间隙锁 很大程度避免

# 3.2 脏读、不可重复读、幻读

# 概念定义

  • 脏读：读到别的事务未提交的数据
  • 不可重复读：同一事务内两次读同一行，结果不同（别的事务 UPDATE 并提交）
  • 幻读：同一事务内两次范围读，行数不同（别的事务 INSERT/DELETE 并提交）

# 底层原理

  • 脏读：RU 无版本控制
  • 不可重复读：RC 下每次新快照，或 RR 下「当前读」与「快照读」混用
  • 幻读：RR 快照读靠 MVCC；当前读靠 Next-Key Lock 防幻读

# 示例 SQL

-- 幻读演示（RR + 快照读）
-- A: START TRANSACTION; SELECT COUNT(*) FROM orders WHERE status=0;  -- 10
-- B: INSERT INTO orders(status) VALUES(0); COMMIT;
-- A: SELECT COUNT(*) FROM orders WHERE status=0;  -- 仍 10（快照读）
-- A: SELECT COUNT(*) FROM orders WHERE status=0 LOCK IN SHARE MODE;  -- 11（当前读）

  • 快照读（一致性读）：普通 SELECT，读 MVCC 历史版本，无锁（RR/RC）

# 底层原理

快照读 → Read View + undo 版本链

-- 当前读
SELECT * FROM orders WHERE id = 1 FOR UPDATE;
SELECT * FROM orders WHERE id = 1 LOCK IN SHARE MODE;
UPDATE orders SET status = 2 WHERE id = 1;  -- 也是当前读
COMMIT;

# 3.4 undo log 原理

# 概念定义

# 3.5 redo log 原理

# 概念定义

redo log（重做日志） 记录物理页的修改，WAL（Write-Ahead Logging）：先写 log，再异步刷脏页，保证崩溃恢复。

# 底层原理

  • 循环写：ib_logfile0/1，innodb_log_file_size × 文件数 = 总 redo 空间
  • LSN（Log Sequence Number）单调递增，标记 redo 进度
  • 崩溃恢复：从 checkpoint 起 replay redo 到 Buffer Pool
  • 与 binlog 区别：redo InnoDB 独有、物理页、循环；binlog Server 层、逻辑、归档

两阶段提交（2PC）：prepare redo → 写 binlog → commit redo，保证 redo 与 binlog 一致。

事务修改 → Buffer Pool 脏页 + redo log buffer
         → commit 时 redo prepare + binlog + redo commit
         → 后台刷脏页（不确定时刻）

# 3.7 MVCC 底层实现

# 概念定义

Multi-Version Concurrency Control：通过版本链 + Read View 实现无锁一致性读。

# 底层原理

Read View 四字段：

  • m_ids：活跃（未提交）事务 ID 列表
  • min_trx_id：m_ids 最小
  • max_trx_id：下一个将分配的事务 ID
  • creator_trx_id：创建该 Read View 的事务 ID

可见性规则（简化）：

  1. trx_id == creator_trx_id → 可见（自己的修改）
  2. trx_id < min_trx_id → 可见（已提交）
  3. trx_id >= max_trx_id → 不可见
  4. trx_id in m_ids → 不可见（活跃未提交）
  5. 否则可见

沿 undo 版本链找第一个可见版本。

RR vs RC：RR 第一次快照读建 View 后不变；RC 每次 SELECT 新建 View。

# 示例 SQL

-- 实验：RR 下 Read View 不变
-- 会话 A                    会话 B
START TRANSACTION;          INSERT INTO t VALUES(2); COMMIT;
SELECT * FROM t;            -- 看到不含新行
-- A 再 SELECT 仍不含 B 插入（快照读）
COMMIT;

# 4.3 行锁（Record Lock）

# 概念定义

# 4.4 临键锁（Next-Key Lock）

# 概念定义

# 8.2 MySQL InnoDB 高频面试题（含标准答案）

# Q1：InnoDB 和 MyISAM 的区别？为什么生产用 InnoDB？

答：InnoDB 支持事务、行锁、MVCC、外键、聚簇索引和 redo 崩溃恢复；MyISAM 无事务、表锁、非聚簇索引，崩溃易损坏。OLTP 需要并发写和一致性，故生产默认 InnoDB。

# Q2：什么是聚簇索引？为什么必须有主键？

答：聚簇索引叶子节点存储完整行，InnoDB 表数据按主键 B+ 树组织，每表仅一个。必须有主键是因为数据物理存储依赖主键排序；若无显式主键，会选择第一个 UNIQUE NOT NULL 或隐式 6 字节 ROW_ID。

# Q3：什么是回表？如何减少回表？

答：通过二级索引查到主键后，再到聚簇索引取全行叫回表。减少方式：覆盖索引（查询列都在索引中）、ICP 减少无效回表、合适联合索引。

# Q4：联合索引 (a,b,c) 哪些 WHERE 能用索引？

答：从 a 开始连续匹配：a；a,b；a,b,c；a,b,c 前缀。单独 b 或 b,c 不能用。a>1 and b=2 只用到 a。范围 a 后 b 通常用不上索引。

# Q5：RR 和 RC 区别？MySQL 默认什么？

答：InnoDB 默认 RR。RR 第一次一致性读创建 Read View 并复用，同一事务 repeatable；RC 每次 SELECT 新 Read View，能读到别的事务已提交更新。RC 间隙锁少，并发高。

# Q6：什么是幻读？InnoDB 如何解决？

答：同一事务两次范围读行数不同。快照读靠 MVCC 读历史版本避免；当前读靠 Next-Key Lock 锁间隙防止别的事务 INSERT。RR 下快照读不幻读。

# Q7：redo log 和 binlog 区别？

答：redo 是 InnoDB 物理页 WAL，循环写，崩溃恢复；binlog 是 Server 层逻辑日志，归档与主从复制。事务提交通过两阶段提交保证两者一致。

# Q8：什么是 MVCC？Read View 如何判断可见性？

答：多版本并发控制，通过 undo 版本链 + Read View 实现无锁一致性读。规则：trx_id 等于 creator 可见；小于 min_trx_id 可见；大于等于 max_trx_id 不可见；在 m_ids 中不可见；否则可见。沿版本链找首个可见版本。

# Q9：什么是当前读和快照读？

答：快照读是普通 SELECT，读 MVCC 版本，不加锁（RR/RC）。当前读是 SELECT FOR UPDATE/LOCK IN SHARE MODE 及 DML，读最新记录并加锁。

# Q10：Next-Key Lock、Record Lock、Gap Lock 关系？

答：Record Lock 锁索引记录；Gap Lock 锁记录间间隙防 INSERT；Next-Key = Record + Gap，锁左开右闭区间。RR 下当前读默认 Next-Key。

# Q11：什么情况下会死锁？如何处理？

答：两事务以不同顺序加锁、gap 与 insert intention 冲突等。InnoDB 自动检测并回滚代价小的事务。应用层固定加锁顺序、缩短事务、改 RC、捕获死锁重试、保证 WHERE 走索引缩小锁范围。

# Q12：索引失效的常见场景？

答：对索引列用函数或运算、隐式类型转换、联合索引不满足最左、OR 一侧无索引、优化器判断全表更优（小表）、统计信息过期。用 EXPLAIN 和 ANALYZE TABLE 验证。

# Q13：EXPLAIN 中 type 各值含义？哪个需优化？

答：system>const>eq_ref>ref>range>index>ALL。ALL 全表扫描通常需优化；index 扫描整棵索引树，也可能慢。还要看 rows 和 Extra。

# Q14：LIMIT 100000, 20 为什么慢？怎么优化？

答：需扫描 100020 行再丢弃前 100000。优化：用 id > last_id 游标分页；或子查询先覆盖索引取 id 再 JOIN 主表。

# Q15：主从延迟原因？业务怎么处理？

答：从库回放慢（大事务、单线程、硬件差）、DDL、大表无 PK。业务上：写后关键读走主库；异步补偿；并行复制；监控 Seconds_Behind_Master。

# Q16：binlog 三种格式区别？生产用哪种？

答：STATEMENT 记 SQL，体积小但不安全函数；ROW 记行变更，准确，推荐；MIXED 混合。生产用 ROW 保证主从一致。

# Q17：innodb_flush_log_at_trx_commit 取值含义？

答：0 每秒刷盘可能丢 1 秒；1 每次 commit fsync 最安全；2 每次 write 到 OS cache 每秒 fsync，可能丢 1 秒 OS 宕机数据。金融主库常用 1。

# Q18：Buffer Pool 是什么？命中率低怎么办？

答：InnoDB 缓存数据页和索引页的内存区。命中率低则增大 innodb_buffer_pool_size、优化 SQL 减少全表扫、避免大查询污染 LRU。

# Q19：分库分表后 ID 怎么生成？

答：常用雪花算法（趋势递增、全局唯一）、号段模式（Leaf/DB 批量取）、Redis INCR。避免单表 AUTO_INCREMENT 冲突和 UUID 随机主键性能问题。

# Q20：长事务有什么危害？

答：undo 无法 purge 导致空间膨胀；持锁阻塞其他事务；从库复制延迟；Buffer Pool 脏页多。解决：缩小 @Transactional 范围、监控 innodb_trx、避免事务内慢 RPC。

# Q21：什么是覆盖索引和 ICP？

答：覆盖索引是查询列全在索引中，Extra 为 Using index，无需回表。ICP 是条件下推到存储引擎层在索引遍历时过滤，Extra 为 Using index condition，减少回表次数。两者不同，可同时出现。

# Q22：为什么推荐自增主键？

答：插入集中在 B+ 树最大页，减少页分裂和碎片；二级索引叶子存主键，主键稳定且短，节省空间；随机主键（UUID）导致频繁分裂和缓冲池污染。

# Q23：UPDATE/DELETE 的 WHERE 为什么必须走索引？

答：否则 InnoDB 对聚簇索引全表扫描并对每条记录加 next-key lock，等价锁全表，并发急剧下降且易死锁。

# Q24：如何实现「SELECT 再 UPDATE」的库存扣减安全？

答：禁止先 SELECT 后 UPDATE。用单条 UPDATE stock SET s=s-1 WHERE id=? AND s>=1 判断 affected rows；或 SELECT FOR UPDATE 在同一事务内锁定后再改。

# Q25：两阶段提交（redo + binlog）为什么需要？

答：若只写 redo 未写 binlog 就 crash，恢复后数据有但 binlog 无，从库缺失。若 binlog 先写 redo 未 commit 就 crash，恢复回滚但 binlog 已有，主从不一致。prepare/commit 与 binlog 顺序保证一致。
