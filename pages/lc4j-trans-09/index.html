# 智能体

注意

本节介绍如何使用 langchain4j-agentic 模块构建智能体 AI 应用。请注意，整个模块目前仍被视为实验性，未来版本可能发生变化。

# 智能体系统

尽管对于 AI 智能体尚无普遍公认的统一定义，但若干新兴模式已展示出如何协调并组合多个 AI 服务的能力，以构建能够完成更复杂任务的 AI 融合应用。这些模式通常被称为「智能体系统（agentic systems）」或「智能体 AI（agentic AI）」。它们通常借助大语言模型（LLM）来编排任务执行、管理工具使用，并在多次交互中维持上下文。

根据 Anthropic 研究人员近期发表的文章 (opens new window)，这些智能体系统架构可分为两大类：工作流（workflows）与纯智能体（pure agents）。

本教程讨论的 langchain4j-agentic 模块提供一组抽象与工具，帮助你构建工作流型与纯智能体型 AI 应用。它允许你定义工作流、管理工具使用，并在与不同 LLM 的交互中维持上下文。

# LangChain4j 中的智能体

LangChain4j 中的智能体使用 LLM 执行特定任务或一组任务。智能体可以像普通 AI 服务一样，用仅含单个方法的接口定义，只需在该方法上添加 @Agent 注解。

public interface CreativeWriter {

    @UserMessage("""
            You are a creative writer.
            Generate a draft of a story no more than
            3 sentences long around the given topic.
            Return only the story and nothing else.
            The topic is {{topic}}.
            """)
    @Agent("Generates a story based on the given topic")
    String generateStory(@V("topic") String topic);
}

智能体还必须在智能体系统内拥有唯一标识其自身的名称。该名称可在 @Agent 注解中指定，也可通过 agent builder 的 name 方法以编程方式指定。若未指定，则名称取自标注了 @Agent 的方法名。

随后可使用 AgenticServices.agentBuilder() 方法构建该智能体实例，指定接口与要使用的对话模型。

@Agent(outputKey = "story", description = "Generates a story based on the given topic")

# AgenticScope 简介

langchain4j-agentic 模块引入 AgenticScope 概念，即参与智能体系统的各智能体之间共享的数据集合。AgenticScope 用于存储共享变量：智能体可写入以传递其产生的结果，其他智能体可读取以汇总执行任务所需信息。这使智能体能够有效协作，按需共享信息与结果。

AgenticScope 还会自动记录其他相关信息，例如所有智能体调用及其响应的序列。它在智能体系统的主智能体被调用时自动创建，并在必要时通过回调以编程方式提供。AgenticScope 的不同用法将在讨论 langchain4j-agentic 实现的智能体模式时，结合实例加以说明。

# 工作流模式

langchain4j-agentic 模块提供一组抽象，用于以编程方式编排多个智能体并创建工作流型智能体模式。这些模式可组合以构建更复杂的工作流。

# 顺序工作流

顺序工作流是最简单的模式：多个智能体依次调用，前一个智能体的输出作为后一个智能体的输入。当你有一系列须按特定顺序执行的任务时，此模式很有用。

例如，可为前面定义的 CreativeWriter 智能体补充一个 AudienceEditor 智能体，用于编辑生成的故事以更好契合特定受众：

        Return only the story and nothing else.
        The story is "{{story}}".
        """)
    @Agent("Edits a story to better fit a given audience")
    String editStory(@V("story") String story, @V("audience") String audience);

# 循环工作流

更充分利用 LLM 能力的常见方式，是反复调用能编辑或改进文本的智能体，对故事等文本进行迭代精炼。这可通过循环工作流模式实现：在满足特定条件前多次调用智能体。

可使用 StyleScorer 智能体，根据风格与要求的契合程度生成分数。

            The story is: "{{story}}"

exitCondition 方法接受 Predicate<AgenticScope> 参数，默认在每次智能体调用后求值，条件满足即退出循环，以尽可能减少智能体调用次数。也可通过循环构建器的 testExitAtLoopEnd(true) 方法，仅在每轮循环结束时检查退出条件，从而强制调用所有智能体后再测试条件。此外，exitCondition 还可接受 BiPredicate<AgenticScope, Integer>，第二个参数为当前循环迭代计数。例如，以下循环定义：

UntypedAgent styleReviewLoop = AgenticServices
        .loopBuilder()
        .subAgents(styleScorer, styleEditor)
        .maxIterations(5)
        .testExitAtLoopEnd(true)
        .exitCondition( (agenticScope, loopCounter) -> {
            double score = agenticScope.readState("score", 0.0);
            return loopCounter <= 3 ? score >= 0.8 : score >= 0.6;
        })
        .build();

# 并行工作流

有时需要并行调用多个智能体，尤其当它们可基于相同输入独立工作时。这可通过并行工作流模式实现：同时调用多个智能体，并将其输出合并为单一结果。

例如，使用电影与美食专家，根据特定氛围生成若干晚间计划，将电影与匹配该氛围的餐食组合。

# 并行映射工作流

并行映射工作流是并行工作流的变体：同一子智能体对集合中每项并行执行多次。换言之，它对列表各项进行 map，对每项独立调用同一子智能体。当你需要对一批输入并发执行相同操作时很有用。

        The person has a name and a zodiac sign. Use both to create a personalized horoscope.
        """)
    @Agent(description = "An astrologist that generates horoscopes for a person", outputKey = "horoscope")

# 异步智能体

默认情况下，所有智能体调用在与智能体系统根智能体相同的线程中执行，因此是同步的，即智能体系统会等待每个智能体完成后再继续下一个。然而在许多场景下这并非必要，将智能体异步调用可使智能体系统继续执行而无需等待该智能体完成。

因此可通过 agent builder 的 async 方法将智能体标为异步。此时该智能体的调用在独立线程中执行，智能体系统继续执行而不等待其完成。异步智能体的结果完成后即写入 AgenticScope，仅当后续智能体调用需要该结果作为输入时，AgenticScope 才会阻塞等待。

例如，由于 FoodExpert 与 MovieExpert（并行工作流一节讨论）彼此独立，将它们标为异步后，即使在顺序工作流中使用也会同时执行。

FoodExpert foodExpert = AgenticServices
        .agentBuilder(FoodExpert.class)
        .chatModel(BASE_MODEL)
        .async(true)
        .outputKey("meals")
        .build();

MovieExpert movieExpert = AgenticServices
        .agentBuilder(MovieExpert.class)
        .chatModel(BASE_MODEL)
        .async(true)
        .outputKey("movies")
        .build();

EveningPlannerAgent eveningPlannerAgent = AgenticServices
        .sequenceBuilder(EveningPlannerAgent.class)

# 错误处理

在复杂智能体系统中，许多情况可能出错，例如智能体未能产生结果、外部工具不可用，或智能体执行过程中发生意外错误。

因此，errorHandler 方法允许为智能体系统提供错误处理器，即将 ErrorContext（定义如下）转换为 ErrorRecoveryResult 的函数：

record ErrorContext(String agentName, AgenticScope agenticScope, AgentInvocationException exception) { }
1

  1. ErrorRecoveryResult.throwException()：默认行为，将引发问题的 Exception 向上传播至根调用方

  3. ErrorRecoveryResult.result(Object result)：忽略问题，将提供的结果作为失败智能体的输出返回

public interface EveningPlannerAgent {

    @ParallelAgent( outputKey = "plans", 
            subAgents = { FoodExpert.class, MovieExpert.class })

    @ParallelExecutor
    static Executor executor() {
        return Executors.newFixedThreadPool(2);

    @Output
    static List<EveningPlan> createPlans(@V("movies") List<String> movies, @V("meals") List<String> meals) {
        List<EveningPlan> moviesAndMeals = new ArrayList<>();
        for (int i = 0; i < movies.size(); i++) {
            if (i >= meals.size()) {
                break;
            }
            moviesAndMeals.add(new EveningPlan(movies.get(i), meals.get(i)));
        }
        return moviesAndMeals;
    }
}

# 纯智能体 AI

迄今所有智能体均通过确定性工作流连接组合为智能体系统。但在某些场景下，智能体系统须更灵活自适应，允许智能体根据上下文与先前交互结果决定如何继续。这通常称为「纯智能体 AI（pure agentic AI）」。

    private final Map<String, Double> accounts = new HashMap<>();

    void createAccount(String user, Double initialBalance) {
        if (accounts.containsKey(user)) {
            throw new RuntimeException("Account for user " + user + " already exists");

        accounts.put(user, initialBalance);

        if (balance == null) {
            throw new RuntimeException("No balance found for user " + user);
        }
        return balance;
    }

    @Tool("Credit the given user with the given amount and return the new balance")
    Double credit(@P("user name") String user, @P("amount") Double amount) {
        Double balance = accounts.get(user);
        if (balance == null) {
            throw new RuntimeException("No balance found for user " + user);
        }
        Double newBalance = balance + amount;
        accounts.put(user, newBalance);
        return newBalance;
    }

    @Tool("Withdraw the given amount with the given user and return the new balance")
    Double withdraw(@P("user name") String user, @P("amount") Double amount) {
        Double balance = accounts.get(user);
        if (balance == null) {
            throw new RuntimeException("No balance found for user " + user);
        }
        Double newBalance = balance - amount;
        accounts.put(user, newBalance);
        return newBalance;
    }
}

# 监督者设计与定制

更一般地，可能存在无法事先确定应返回监督者生成的摘要还是最后调用智能体响应的情况。为此提供了第二个智能体，将这两种可能响应与原用户请求一并传入，对它们评分以决定哪个更符合请求，从而决定返回哪一个。

# 自定义智能体模式

迄今讨论的智能体模式由 langchain4j-agentic 模块开箱即用提供，但若无一符合应用具体需求怎么办？此时可创建自己的自定义模式，以符合需求的方式编排一组子智能体的交互。

更具体地说，智能体模式即对其协调的子智能体的执行计划规范。该计划可通过实现以下 Planner 接口定义：

注意引入 firstAction 仅因为在许多情况下，用独立回调定义 Planner 要调用的第一个智能体很方便。若无需此区分，它提供默认实现，仅将调用转发给 nextAction，因此不必强制覆盖。

firstAction 与 nextAction 返回的 Action 类表示智能体模式的下一步，可以是接下来要调用的一个或多个子智能体列表，或表示执行已完成的信号。若动作仅指定一次子智能体调用，则顺序执行，且在与执行规划器相同的线程中；若多于一个，则使用提供的 Executor 或 LangChain4j 默认执行器并行执行。

# 目标导向智能体模式

工作流模式与监督者智能体代表可能智能体系统的两个极端：前者完全确定、僵化，须事先决定调用序列；后者完全灵活自适应，但将调用序列的决定委托给非确定性 LLM。然而在某些情况下，介于两者之间的折中更合适——允许智能体以相对灵活的方式朝特定目标工作，同时以算法方式决定如何调用这些智能体。

为实践此方法，不仅整个智能体系统须定义目标，每个子智能体也须声明自身的前置与后置条件。这对于计算以最快方式达成目标的智能体调用序列是必要的。然而，这些信息在智能体系统中已隐式存在——前置与后置条件无非是各智能体所需输入与产生输出，最终目标即是整个智能体系统期望的输出。

遵循此思路，可计算参与智能体系统的所有子智能体的依赖图，然后实现能够分析 AgenticScope 初始状态、与期望目标比较，并利用该图确定可达成目标的智能体调用序列的 Planner。

public class GoalOrientedPlanner implements Planner {

    private String goal;

    private GoalOrientedSearchGraph graph;
    private List<AgentInstance> path;

    private int agentCursor = 0;

    @Override
    public void init(InitPlanningContext initPlanningContext) {
        this.goal = initPlanningContext.plannerAgent().outputKey();
        this.graph = new GoalOrientedSearchGraph(initPlanningContext.subagents());
    }

    @Override
    public Action firstAction(PlanningContext planningContext) {
        path = graph.search(planningContext.agenticScope().state().keySet(), goal);
        if (path.isEmpty()) {
            throw new IllegalStateException("No path found for goal: " + goal);
        }
        return call(path.get(agentCursor++));
    }

    @Override
    public Action nextAction(PlanningContext planningContext) {
        return agentCursor >= path.size() ? done() : call(path.get(agentCursor++));
    }
}

# 点对点智能体模式

迄今讨论的所有智能体系统均基于集中式层次架构。事实上，所有工作流模式都有明确定义的顶层智能体，以编程预定方式协调多个子智能体。即使监督者模式因 LLM 规划智能体而更灵活动态，仍依赖协调智能体控制各子智能体交互。此类架构适用于许多应用与场景，但在可扩展性与容错方面也可能存在局限。因此我们可能希望为多智能体系统提供对等的点对点替代方案，通过更去中心化、分布式的策略克服这些局限。

在点对点智能体系统中没有顶层智能体，所有智能体均为通过对等关系协调的平等节点，协调通过 AgenticScope 状态完成。具体而言，当 AgenticScope 状态变量中存在某智能体所需输入时，该智能体被触发。随后，由其他智能体输出引起的一个或多个变量变化，可再次触发该智能体调用。过程在 AgenticScope 达到稳定状态且无法再调用任何智能体时终止，或在满足预定义退出条件时终止，或达到最大智能体调用次数时终止。实现该点对点智能体模式的 Planner 可如下编写：

public class P2PPlanner implements Planner {

    private final int maxAgentsInvocations;
    private final BiPredicate<AgenticScope, Integer> exitCondition;

    private int invocationCounter = 0;
    private Map<String, AgentActivator> agentActivators;

    public P2PPlanner(int maxAgentsInvocations, BiPredicate<AgenticScope, Integer> exitCondition) {
        this(null, maxAgentsInvocations, exitCondition);
    }

    @Override
    public void init(InitPlanningContext initPlanningContext) {
        this.agentActivators = initPlanningContext.subagents().stream().collect(toMap(AgentInstance::agentId, AgentActivator::new));
    }

    @Override
    public Action nextAction(PlanningContext planningContext) {
        if (terminated(planningContext.agenticScope())) {
            return done();
        }

        AgentActivator lastExecutedAgent = agentActivators.get(planningContext.previousAgentInvocation().agentId());
        lastExecutedAgent.finishExecution();
        agentActivators.values().forEach(a -> a.onStateChanged(lastExecutedAgent.agent.outputKey()));

        return nextCallAction(planningContext.agenticScope());
    }

    private Action nextCallAction(AgenticScope agenticScope) {
        AgentInstance[] agentsToCall = agentActivators.values().stream()
                .filter(agentActivator -> agentActivator.canActivate(agenticScope))
                .peek(AgentActivator::startExecution)
                .map(AgentActivator::agent)
                .toArray(AgentInstance[]::new);
        invocationCounter += agentsToCall.length;
        return call(agentsToCall);
    }

    private boolean terminated(AgenticScope agenticScope) {
        return invocationCounter > maxAgentsInvocations || exitCondition.test(agenticScope, invocationCounter);
    }
}

# 黑板智能体模式

P2P 模式并行激活所有就绪智能体，将它们视为平等节点。然而在某些场景下，应由集中式调度器决定下一步触发哪个智能体，并在多个智能体均可贡献时进行冲突消解。这就是黑板模式：智能体作为知识源将部分结果发布到 AgenticScope（黑板），集中式规划器在每一步后检查黑板以激活最合适的智能体。

与 P2P 类似，当作用域中存在智能体全部参数时，智能体隐式激活。关键区别在于每步仅触发一个智能体；当多个智能体就绪时，由 ConflictResolutionStrategy 决定优先级。若未提供策略，则使用 subAgents 方法中的声明顺序作为默认决胜规则。

BlackboardPlanner 在目标谓词满足、无智能体可触发（静默）或达到最大调用次数时终止。默认情况下，目标谓词检查规划器的 outputKey 是否存在于作用域中——这是最常见的终止条件：

# 投票智能体模式

迄今讨论的智能体模式编排的是做不同事情的智能体——拆分工作、顺序任务或路由决策。然而在某些情况下，你希望多个智能体独立处理同一问题，然后聚合其答案以产生更稳健的结果。这就是投票（或委员会）模式：对所有子智能体基于相同输入并行运行，将其输出收集为投票，并通过可插拔聚合策略调和。

该模式尤其适用于分类、内容审核、风险评估，以及任何共识比单一智能体判断更可靠的决策场景。通过让具有不同提示、模型或视角的智能体分析相同输入，可降低单一智能体偏见或错误传播到最终结果的概率。

VotingPlanner 并行分派所有子智能体，等待全部完成后，使用 VotingStrategy 聚合其输出：

public class VotingPlanner implements Planner {

    private final VotingStrategy strategy;

    private List<AgentInstance> subagents;
    private int completedCount;
    private final List<Object> votes = new ArrayList<>();

    public VotingPlanner() {
        this(VotingStrategy.majority());
    }

    public VotingPlanner(VotingStrategy strategy) {
        this.strategy = strategy;
    }

    @Override
    public void init(InitPlanningContext initPlanningContext) {
        this.subagents = initPlanningContext.subagents();
    }

    @Override
    public Action firstAction(PlanningContext planningContext) {
        if (subagents.isEmpty()) {
            return done();
        }
        return call(subagents);
    }

    @Override
    public Action nextAction(PlanningContext planningContext) {
        votes.add(planningContext.previousAgentInvocation().output());
        completedCount++;

        if (completedCount < subagents.size()) {
            return noOp();
        }

        return done(strategy.aggregate(votes));
    }

    @Override
    public AgenticSystemTopology topology() {
        return AgenticSystemTopology.STAR;
    }
}

# 辩论智能体模式

迄今讨论的模式要么一次性分派智能体（投票），要么基于数据可用性激活（黑板、P2P），要么朝目标顺序执行（GOAP）。无一支持对抗式精炼——智能体可见彼此推理并迭代修正立场的流程。辩论模式填补此空白：智能体并行生成独立答案，然后进入批判轮次，可阅读完整辩论历史并精炼论点。轮次持续至智能体收敛于相同答案或达到最大轮数，此时由裁判智能体给出最终裁决。

该模式尤其适用于事实核查、风险评估、代码审查，以及任何通过暴露于竞争性论点可提升输出质量的领域。通过迫使智能体面对并回应彼此推理，辩论模式可发现单一智能体可能遗漏的问题，并通过对抗性审查过滤误报。

该模式通过 DebatePlanner 实现，将其子智能体划分为辩手（除最后一个外的全部）与裁判（最后注册的子智能体）。规划器配置两个参数：maxRounds（默认 3）与 ConvergenceStrategy（默认 unanimous()）。

初始化时，规划器验证至少注册三个子智能体（两名辩手与一名裁判）并相应拆分列表。第一个动作在 AgenticScope 中播种空 debateContext 键——这是必要的，因为辩手智能体通过 @V(DEBATE_CONTEXT_KEY) 引用该键，没有它第一轮将因 MissingArgumentException 失败。然后并行分派所有辩手。

每个辩手完成时，在框架锁下序列化调用 nextAction。规划器将各输出记录在以智能体名为键的 Map 中，直至所有辩手完成前返回 noOp()。全部响应收集后，检查两个条件：ConvergenceStrategy 是否报告收敛，以及当前轮次是否达到 maxRounds。任一满足即进入裁判阶段——将辩论上下文格式化为 AgentName: "response" 条目（每行一个），写入作用域，并分派裁判智能体。裁判完成时，规划器以裁判输出为最终结果返回 done()。若既未收敛也未达轮次上限，规划器将当前辩论上下文写入作用域，递增轮次计数器，并重新分派所有辩手进入另一批判轮次，使其可见并回应彼此先前论点。

ConvergenceStrategy 是仅含 hasConverged(Collection positions) 方法的函数式接口。提供两种内置策略：unanimous() 检查所有立场是否完全相等（适用于 APPROVE/REJECT 等基于标签的决策），unanimousLastWord() 从各立场提取最后一个词、规范为大写并检查所有智能体是否以相同裁决结尾。对于更细致的收敛逻辑——如语义相似度或基于阈值的同意——用户可提供自定义策略 lambda。

# AgenticScope 注册表与持久化

AgenticScope 是在智能体系统执行期间创建和使用的瞬态数据结构。每个用户每个智能体系统有一个 AgenticScope。对于无状态执行（不使用记忆时），AgenticScope 在执行结束时自动丢弃，其状态不会持久化到任何地方。

相反，当智能体系统使用记忆时，AgenticScope 保存在内部注册表中。此时 AgenticScope 永久保留在注册表中，使用户能够以有状态、对话式方式与智能体系统交互。因此，当具有特定 ID 的 AgenticScope 不再需要时，须显式从注册表驱逐。为此，智能体系统的根智能体须实现 AgenticScopeAccess 接口，以便对其调用 evictAgenticScope 方法，传入要从注册表移除的 AgenticScope 的 ID。

agent.evictAgenticScope(memoryId);
1

AgenticScope 及其注册表均为纯内存数据结构。这对简单智能体系统通常足够，但在某些情况下将 AgenticScope 状态持久化到更耐久存储（如数据库或文件系统）可能有用。为此 langchain4j-agentic 模块提供 SPI 以接入实现 AgenticScopeStore 接口的自定义持久层。可编程设置该持久层：

AgenticScopePersister.setStore(new MyAgenticScopeStore());
1

或使用标准 Java Service Provider 接口，创建名为 META-INF/services/dev.langchain4j.agentic.scope.AgenticScopeStore 的文件，内容为实现 AgenticScopeStore 接口的类的全限定名。

# AgenticScope 与智能体系统可恢复性

配置 AgenticScopeStore 后，langchain4j-agentic 模块提供内置可恢复性支持，使智能体系统在崩溃或进程重启后可从停止处恢复执行。这对包含人在回路步骤的长运行工作流尤其有价值，进程可能有意停止并在稍后重启。

可恢复性基于两种机制协同工作：逐步检查点与规划器执行状态持久化。

每次智能体调用后，当前 AgenticScope 自动检查点到配置的存储。这意味着智能体通过 writeState 写入的所有中间状态均被耐久持久化。此外，执行循环保存规划器内部位置（例如顺序工作流中已到达哪个智能体），以便恢复时工作流从正确步骤继续而非从头开始。

Planner 接口的实现可选择通过两个方法参与此机制：

// Returns the planner's current internal state for persistence

// Restores internal state from a previously saved map
default void restoreExecutionState(Map<String, Object> state) { }

# 与 A2A 服务器的多轮对话

A2A 协议通过消息信封上的 contextId 与 taskId 字段支持多轮对话。contextId 将相关任务分组为一次对话，taskId 引用该对话中的特定任务。省略时 A2A 服务器生成新值；提供时服务器继续现有对话。

要在传出消息信封上传递这些字段，请用 @A2AContextId 与 @A2ATaskId 标注方法参数。这些参数不会作为消息内容发送——而是设置在消息信封上。

public interface ChatAgent {

    @A2AClientAgent(a2aServerUrl = "http://localhost:8080", outputKey = "response")
    String chat(@V("question") String question,
                @A2AContextId @V("contextId") String contextId,
                @A2ATaskId @V("taskId") String taskId);
}

当 @A2AContextId 或 @A2ATaskId 参数还具有可识别名称（可能通过 @V 注解配置）时，响应中服务器分配的值会自动写回 AgenticScope 的该名称下。这支持多轮流程：首次调用捕获 ID，后续调用复用它们。

若方法返回 ResultWithAgenticScope，ID 可直接访问：

public interface ChatAgent {

    @A2AClientAgent(a2aServerUrl = "http://localhost:8080", outputKey = "response")
    ResultWithAgenticScope<String> chat(
            @V("question") String question,
            @A2AContextId @V("contextId") String contextId,
            @A2ATaskId @V("taskId") String taskId);
}

// First turn — server generates contextId and taskId
ResultWithAgenticScope<String> first = chatAgent.chat("hello", null, null);
String contextId = (String) first.agenticScope().readState("contextId");
String taskId = (String) first.agenticScope().readState("taskId");

// Second turn — reuse the server-generated IDs to continue the conversation
ResultWithAgenticScope<String> second = chatAgent.chat("follow-up", contextId, taskId);

# 基于 MCP 的工具智能体

额外的 langchain4j-agentic-mcp 模块允许将单个 MCP (opens new window) 工具包装为智能体系统中的非 AI 智能体。与使用 LLM 的常规智能体不同，MCP 工具智能体直接执行 MCP 工具并返回其结果。这使得可在更大智能体系统中将 MCP 工具与其他智能体组合，而工具执行本身无需涉及 LLM。

要创建 MCP 工具智能体，使用 McpAgent.builder() 并提供 McpClient 实例。构建器向 MCP 服务器查询工具规范（名称、描述、输入模式）并创建将调用转发至该工具的智能体。

例如，若 MCP 服务器暴露 generate_story 工具，可将其包装为非类型化智能体：

McpClient mcpClient = new DefaultMcpClient.Builder()
        .transport(myMcpTransport)
        .build();

UntypedAgent storyGenerator = McpAgent.builder(mcpClient)
        .toolName("generate_story")
        .inputKeys("topic")
        .outputKey("story")
        .build();

String story = (String) storyGenerator.invoke(Map.of("topic", "dragons and wizards"));
